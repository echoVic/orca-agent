# 遗留问题修复设计（v0.5.6 之后）

> 状态：待审阅（2026-10-05）。
> 前提：v0.5.6 发布后，用户要求先修复遗留问题、再升级依赖，computer use 暂缓。
> 三个子项目按顺序进行，各自走规格 → 计划 → 执行：
> 1. 遗留问题修复（本文）；
> 2. 依赖升级（含 TUI 栈与网站）；
> 3. ACP SDK 迁移。
>
> 范围：MCP 两轮工作和 v0.5.6 发版评审留下的已知问题，以及测试对用户主目录的污染。

## 1. 进程信号

### 1.1 `orca exec`：启动之前的空窗

**现状：**
- `run_inner`（`crates/orca-runtime/src/controller.rs`）的启动顺序是：
  1. 启动运行时（`RuntimeHost::start`）；
  2. 启动会话线程，这一步同时在后台开始连接 MCP 服务器；
  3. 调用 `install_termination_signal_handler`，它又在另一个线程上异步注册 SIGINT/SIGTERM。
- 注册生效之前收到的信号按默认方式直接结束进程，于是：
  - 已经启动的 stdio MCP 服务器和任务命令可能残留；
  - 会话没有终止记录；
  - JSONL 输出没有终止事件。

**要求：**
1. **先装好信号处理，再启动。** `run_inner` 一开始，在启动运行时之前，就装好 SIGINT/SIGTERM 处理，并且等注册确实生效之后才继续。
2. **线程启动前的信号先记下。** 线程一启动就立即按现有的中断路径处理：
   - 停止任务命令；
   - 关闭 MCP 注册表，结束 stdio 服务器；
   - 提交终止记录。
3. **退出与提示。**
   - 退出码与现在相同：SIGINT 130，SIGTERM 143。
   - 文本模式在 stderr 说明收到的信号；JSONL 模式照常写出终止事件。
4. **不变的部分：** 宽限期（10 秒）和"第二个信号立即退出"保持现状。Windows 保持现在的 Ctrl+C 处理。

### 1.2 TUI：SIGTERM、SIGHUP 和外部发来的 SIGINT

**现状：**
- TUI 处于 raw 模式，只把 Ctrl+C 当作按键处理。进程收到 SIGTERM、SIGHUP，或别的进程发来 SIGINT 时，按默认方式立即结束，于是：
  - stdio MCP 服务器可能残留，包括还在连接的；
  - 终端停在 raw 模式或备用屏幕；
  - 会话不能正常收尾。

**要求（unix）：**
1. **转成退出事件。** 处理 SIGTERM、SIGHUP、SIGINT：信号变成渲染循环里的一个事件，之后走与正常退出相同的路径（`finish_tui_run`）：
   - 中断正在运行的轮次；
   - 关闭 prestart 注册表和线程的 MCP 服务器；
   - 保存会话；
   - 恢复终端；
   - 终端还在时，打印 `orca --resume <SESSION_ID>`。
2. **退出码为 128 + 信号编号：** SIGINT 130，SIGHUP 129，SIGTERM 143。
3. **SIGHUP 时终端已经不在了：**
   - 不再绘制；
   - 写终端出错一律忽略；
   - 不打印续接命令。
4. **宽限期与第二个信号。** 清理在宽限期（10 秒，与 exec 相同）内没有完成就直接退出；收到第二个信号立即退出。
5. **attach 模式同样适用。** 通过 `orca attach` 连到 daemon 的 TUI 收到信号后，只断开它自己的连接，daemon 的会话不受影响。
6. **Windows 不在本轮**（控制台关闭事件，见第 8 节）。

## 2. 测试隔离与清理

**现状：**
- 跑全量测试会往真实的 `~/.orca/task-sessions` 写目录，截至 2026-10-05 已有 49,262 个，多数只含一个 `tasks.lock`。
- orca-runtime 的 lib 测试已有进程级的临时 `ORCA_HOME`，以及按线程覆盖的机制（`folder_trust::current_orca_home_override`、`history::isolated_test_orca_home`）。
- 但其他测试二进制在没有设置 `ORCA_HOME` 时会退回真实的 `~/.orca`，包括：
  - orca-tui 的测试；
  - 各 crate 的 `tests/*.rs`；
  - 通过 orca-runtime 正式构建运行的测试。

**要求：**
1. **一个解析入口。** Orca 在自己 home（`ORCA_HOME`，否则 `~/.orca`）下读写的路径，都经由 orca-core 里的一个函数解析，包括：
   - 配置；
   - 信任记录；
   - 会话；
   - task-sessions；
   - goals；
   - memory；
   - summary cache；
   - 凭据。

   不属于 Orca home 的路径（沙箱规则、用户 skills 目录等）不在此列。
2. **测试构建默认用临时目录。** 测试构建里，没有设置 `ORCA_HOME`、也没有按线程覆盖时，这个函数返回本进程独有的临时目录。测试构建是指：本 crate 的 `cfg(test)`，以及其他 crate 通过 dev-dependency 打开的 `test-utils` feature。正式构建（`cargo build`、发布产物）的行为不变。
3. **CI 把关。** Linux CI 在测试之后检查 `$HOME/.orca`：测试期间被创建或改动就失败，并列出路径。
4. **清理已有目录：**
   - 修复合入之后，列出 `~/.orca/task-sessions` 下与任何真实会话都对不上的目录。真实会话指 `~/.orca/sessions` 下有记录的会话 id，以及 `sessions-index.sqlite3` 里的会话。
   - 按类别给出数量、示例和时间范围，先给用户看报告。
   - 用户确认后，整体移到 `~/.orca/task-sessions.test-backup-<日期>/`，不删除。
   - 判断不了的目录保留原处。
   - 这是一次性操作，脚本不进仓库。

## 3. MCP 客户端

### 3.1 结构：只挪代码，不改行为

1. **拆分 `crates/orca-mcp/src/client.rs`**（约 6.9k 行）：
   - `registry.rs`：`McpRegistry`，以及状态、订阅、启动等待；
   - `connection_stop.rs`：`McpConnectionStop`；
   - `client.rs`：`McpClient` 的请求、重连和重启。
2. **合并 SSE 解析。** 现在有三处 SSE 解析：
   - streamable HTTP 的响应读取；
   - GET 事件流；
   - `legacy_sse.rs` 的旧版传输。

   合成 `sse.rs` 里的一个增量解码器：按字节流切出事件，支持 CRLF、注释行、多行 `data`，以及 `event`、`id` 字段。三处都改用它。
3. **单独提交。** 这一步单独提交，不改任何行为，由现有测试保证。另外补上解码器自己的单元测试，覆盖：
   - 事件跨两次读取；
   - CRLF；
   - 注释行；
   - 多行 `data`；
   - 没有 `data` 的事件。

### 3.2 等锁时也能取消

- **现状：** 可取消的请求如果排在一个不可取消的重启后面（`list_prompts`、`get_prompt` 等触发的重连），要等那次重启结束才看得到取消。
- **要求：**
  - 可取消的请求等待传输锁时，每 25 ms 检查一次取消，被取消就立即返回 `Cancelled`，不发送请求。
  - 不可取消的请求照旧阻塞等待。

### 3.3 stdio 随时应答服务器的请求

- **现状：** stdio 服务器发来的请求只在有请求进行中时才被读到和应答。空闲时发来的 `ping` 要等下一个请求才回，服务器可能因此判定连接已死。
- **要求：** 由读取线程直接应答，与有没有进行中的请求无关：
  - `ping` 回空结果；
  - 不认识的请求回 JSON-RPC 错误 `-32601`；
  - `elicitation/create` 在有工具调用进行中时，照现在的方式交给它的处理器；没有时回错误 `-32601`。
- 写 stdin 的地方共用一个加锁的写端，请求和应答的行不会交错。

### 3.4 资源列表被截断时告诉模型

- **现状：** `resources/list` 和 `resources/templates/list` 因为超过 100 页或游标重复而提前停止时，错误只记在列表的 `errors` 里，模型通过 `list_mcp_resources` 看到的输出不提。
- **要求：** 工具输出末尾说明列表不完整，以及原因：哪个服务器，是页数上限还是游标重复。

### 3.5 重连的失败记录要准确

1. **什么也没做的重连不清除失败记录。** 另一个请求已经换过传输时，`reconnect` 什么也不做就返回，此时不能清掉别人新记下的失败。只有真正连上的重连才清除记录。
2. **短重连的真实失败立即记录。** 工具调用被取消后的短重连（上限 500 ms），如果是因为启动失败而不是到了上限，就立即记录，服务器立即显示 `Failed`，不再等下一次调用才报告。
   - 是否到了上限，用类型化的结果判断，不匹配错误文字。

### 3.6 登录取消

1. **发现和注册阶段。** 取消发生在 OAuth 发现或动态注册阶段，也就是浏览器打开之前时：
   - 100 ms 内生效；
   - 释放回调端口；
   - 进行中的 HTTP 请求的结果直接丢弃。
2. **取消和浏览器回调同时到达：**
   - 结果只能是"已取消"或"已完成"之一，由现有的一次 CAS 决定。
   - `/mcp` 面板按实际结果显示：取消没赶上时显示 `finishing login…`，不显示 `cancelling login…`。
   - `orca mcp login` 同理。

### 3.7 prestart 警告不重复

- **现状：** 交给线程的 prestart 注册表，警告快照在交接时才取。于是第一条消息之前用 `r` 重连失败的服务器，会先在面板里报一次，再以另一种措辞作为启动警告报一次。
- **要求：**
  - 交接后的启动警告，只包含交接时还没向用户报告过的失败；
  - 措辞与 `/mcp` 的状态一致。

### 3.8 补上没有测试的分支

1. **启动失败后不重复启动服务器。** 线程启动失败或预检失败后，prestart 的服务器保留；下一次启动时，每个服务器仍只启动一次。
2. **端口绑定后立即取消。** 在回调端口绑定之后、打开浏览器之前取消，端口被释放，浏览器不会打开。

## 4. TUI：恢复会话时的消息顺序

**现状：**
- 用 `--continue` 或 `--resume` 恢复会话、并且带了命令行提示词时，如果用户在历史加载完之前按 Enter，问题有两个：
  - 输入的消息会先于命令行提示词发出；
  - 加载进来的历史会把这条消息从屏幕上冲掉。

**要求：**
1. **先暂存。** 启动时要恢复的会话还没加载完（`HistoryLoaded` 之前），按 Enter 只暂存消息：输入框清空，消息留在屏幕上。
2. **按顺序发出。** 历史加载完后：
   - 先发命令行提示词；
   - 再按顺序发暂存的消息，它们像轮次进行中发送的消息一样进入队列；
   - 这些消息都显示在历史之后。
3. **其他情况不变：** 没有恢复会话、或会话已经加载完的情况，行为与现在相同。

## 5. 配置：内联数组里的注释

**现状：**
- `orca mcp add` 和 `remove` 修改带注释的多行内联数组（`mcp_servers = [ … ]`，每行一项）时，每行的注释可能挂到别的条目上，或者丢失。
- `]` 前没有逗号的那条注释，会排成难看的版式（TOML 仍然合法）。

**要求：**
1. **删除条目：** 连同它自己的注释一起删掉，也就是紧挨在它上面的注释行，加上同一行末尾的注释。其他条目的注释不动。
2. **添加条目：** 新条目单独占一行，加在最后一项（及其行尾注释）之后。`]` 前原有的注释仍留在末尾。
3. **其他写法不变：** 单行内联数组和 `[[mcp_servers]]` 表数组的处理方式不变。

## 6. 文档

中英文都要改：
- **`orca-exec`：** `orca exec` 一启动就接管 SIGINT/SIGTERM，收到后：
  - 停止任务命令和 MCP 服务器；
  - 写入终止记录；
  - 以 130 或 143 退出；
  - 第二个信号立即退出。
- **`terminal-ui`：** TUI 收到 SIGTERM、SIGHUP 或 SIGINT 时，像正常退出一样收尾，退出码为 128 + 信号编号。
- **`mcp-integration`：** 资源列表被截断时，模型会看到截断的说明。

## 7. 测试

每一项都先写一个修复前会失败的测试。

**信号：**
- **`tests/signal_contract.rs`：** `orca exec` 配一个启动后立即写下自己 pid 的 stdio 服务器，在服务器刚启动时就发 SIGTERM。断言：
  - orca 以 143 退出；
  - 服务器进程已经不在；
  - JSONL 输出里有终止事件。
- **PTY：**
  - 分别发 SIGTERM 和 SIGHUP，同时配一个慢启动的 MCP 服务器。断言：
    - 退出码分别是 143 和 129；
    - 服务器进程已经不在；
    - SIGTERM 时写出了终端恢复序列，例如关闭 bracketed paste 的 `ESC[?2004l`。
  - 轮次进行中发 SIGTERM：这一轮被中断，进程退出。

**测试隔离：**
- 一个测试在没有设置 `ORCA_HOME` 时解析 Orca home，得到的是进程级临时目录，不是真实的 `~/.orca`。
- CI 检查 `$HOME/.orca` 未被改动。

**MCP：**
- 等锁时取消：持有传输锁的不可取消重启进行时，一个可取消的调用在 25 ms 级别内返回 `Cancelled`，且服务器没收到它。
- stdio 空闲时，服务器发来的 `ping` 立即得到应答；不认识的请求得到 `-32601`。
- 资源列表达到页数上限或游标重复时，`list_mcp_resources` 的输出说明截断。
- 一个请求的重连已经换过传输后，另一个请求的空操作重连不清除前者记下的失败。
- 短重连启动失败（服务器立即退出），服务器立即显示 `Failed`。
- 发现阶段取消登录：100 ms 内返回取消，端口被释放。
- 回调与取消同时到达时，只有一个结果生效，面板显示与之一致。
- 交接后的启动警告不重复面板里已报告过的失败。
- 第 3.8 节的两个分支。

**TUI 顺序：**
- PTY 测试：`--resume latest "prompt"` 在历史加载前输入一条消息，mock 记录的用户消息顺序是：恢复前的消息 → 命令行提示词 → 暂存的消息。暂存的消息显示在历史之后。

**配置：**
- 带注释的多行内联数组：增删条目后，每条注释仍挂在原来的条目上，`]` 前的注释留在末尾。
- 至少覆盖三种写法：条目上方的注释、行尾注释、`]` 前的注释。

**全量：**
- 用 `env -u NODE_OPTIONS` 跑：
  - workspace `ci` profile；
  - orca-tui lib（ci-serial）；
  - PTY；
  - 两个校验脚本。
- Linux 和 Windows CI 通过。
