# Orca 子代理运行时优化方案

设计日期：2026-09-13；实施状态更新：2026-09-14。核心调度、等待、恢复、全树预算结算、交付和只读调查收敛路径已经实施，并已使用真实 DeepSeek 模型完成三类压力场景和受控四路并发 A/B。代码事实、测试结果和剩余验收边界以 [实施进度](subagent-runtime-optimization-progress.md) 为准。

本文是本轮目标架构与优先级的唯一依据，取代旧方案中“保留默认 6”“超限立即拒绝”以及把已有能力继续列为未来功能的建议。不保留旧参数、旧同步执行后端或旧状态协议的兼容层。

## 1. 确定的产品决策

1. **默认允许 32 个子代理同时执行，运行容量满时默认排队。** 32 是用户可调的容量上限，不是每次任务的派单数量目标，也不附加“通常只派 2—3 个”的固定限制。
2. 默认 `adaptive` 委派：主代理保留关键路径与结果整合，独立探索、实现、验证分支尽早派发。用户明确禁止或限定委派时遵守该要求。
3. 普通子代理、嵌套子代理、Workflow 内的 LLM 子任务、UI continue 和恢复执行共用准入。同步/后台只是调用方是否等待，不再各自拥有运行池。
4. 等待子任务的代理释放执行名额，恢复执行前重新取得名额。不能靠提高上限掩盖祖先占满容量导致的死锁。
5. 子代理生命周期始终由 runtime 持有。容量不足不要求模型重复提交；排队、完成、失败、取消和恢复都有持久事实。
6. 不设置通用子代理硬超时。等待时长、明确的任务期限、预算和资源容量分别管理。
7. 沿用 RuntimeHost、AgentController、ChildAgentCoordinator、TaskRegistry、Surface 和 continuation；调度队列是既有任务事实的投影，不另建一套任务数据库或状态真相。

## 3. 配额的作用域和默认值

```toml
[subagents]
delegation = "adaptive"
max_running = 32
max_queued = 256
max_live_tasks = 512
max_depth = 2
max_investigation_turns = 6
max_investigation_tool_calls = 8
```

`max_running=32` 和满额排队是确定决策；256/512 是本方案提出的可调资源边界，不是对 Grok 默认值的描述。三个容量值都要求正整数；用 `delegation="off"` 关闭新委派，不用容量 0 表示关闭。

- **作用域：一棵根任务树。** 根会话中的普通子任务、任意深度后代、Workflow LLM 子任务、UI 续跑都继承同一个 `execution_scope_id`。已有 scope 内重载任务不生成新的配额池；独立根会话各有一个池。
- 根主代理不占这 32 个子代理名额，因此它仍可响应用户、取消任务和整合结果。根与子任务都受真实 provider 请求限制和宿主资源约束。
- `max_running` 计算已准入且尚未安全释放的执行 lease，包括正在启动、请求模型、执行前台工具、停止但尚未确认静默的任务。不能只依据 UI 的 `running` 字段计数。
- `max_queued` 限制待启动的新任务。`max_live_tasks` 限制该树内全部非终态子任务，包括运行、排队、等待子任务、等待用户和恢复等待，以免释放执行名额后仍无限积累进程或会话。
- 已接受任务的安全让出与重新就绪不受“新任务队列已满”阻挡；恢复队列受 `max_live_tasks` 约束，与新任务队列共享公平调度。不能让一个已接受的父代理因恢复队列满而无法收尾。
- 已完成历史任务不占以上配额；历史留存与分页另行管理。等待代理完成持久 checkpoint 后释放执行名额。当前 UI 仍以活动 RuntimeThread handle 继续子对话，因此安全等待只释放 lease，不提前关闭线程；将来只有在 actor 可透明重载并重绑 UI handle 后才卸载上下文。执行名额和内存驻留分别计量。
- Workflow 可再施加更小的 run 配额，但不得越过根任务树上限。并行 shell 进程与外部请求有自己的资源池，不能把 32 个 agent 名额解释成 32 个任意进程的总上限。
- 多根会话的宿主总量由宿主资源管理与 provider 限流单独控制，不暗设一个 6 的宿主上限抵消这里的默认 32；存在实际限制时展示来源和等待原因。

删除 `max_parallel`，不保留别名。满额排队是固定语义，不新增 `queue|fail` 模型选项；只有任务非法、无权限、预算已确定耗尽或队列/存活数量达到边界等原因才拒绝或停止。

## 4. 单一路径：提交、排队、取得执行权

### 4.1 提交即获得持久句柄

`subagent` 校验角色、权限、深度、所属根任务、必要预算条件和任务数量边界，冻结模型/工具/权限/目标/工作区快照，然后持久化任务与提交记录。容量不足时正常返回：

```json
{
  "task_id": "task-42",
  "status": "queued",
  "wait_reason": "execution_capacity",
  "scope": {"running": 32, "limit": 32},
  "message": "任务已接受，空出执行名额后自动运行；无需重复提交。"
}
```

不把 queued 返回成工具失败，也不虚报 started。排队期间不启动子进程、不复制完整历史、不创建 worktree；保存必要的启动材料与源码基准引用。实际启动时核对授权与工作区前提：角色/模型沿用冻结值，权限撤销必须收窄或阻止启动。需要固定代码输入的任务明确使用已记录的提交或快照，不能默默把晚到的工作区变化当成原始输入。

新任务队列或存活数量确实满时返回 `queue_full` 或 `live_task_limit`，明确 `accepted=false`、没有创建任务，并附现有任务的观察入口。调用方得到确定背压，不进入盲目重试。启动工具没有等待队列空位的隐藏长阻塞。

### 4.2 持久准入事务

在现有 runtime owner 下串行决策，容量检查、执行 lease、预算预留与启动意图必须作为一个持久事务提交。共享 atomic 的“先读计数、再增加”不能充当跨线程、跨进程的原子准入。

派发顺序：校验可运行条件 → 提交启动意图及容量/预算预留 → 按 attempt 身份启动 → worker 确认 → 执行。每个 worker 启动时验证 owner epoch 和 execution lease；没有有效 lease 不可执行。

同一 tool-call 的投递重试通过 runtime 生成的提交身份返回原 task_id。不同调用即使 prompt 相同，也不自动视为重复任务。

进程启动与持久事务无法组成一个原子操作：通过 attempt、owner epoch、启动回执和恢复核对收敛。不能以“事务已提交”证明进程只启动一次，也不能在启动状态不明时直接重跑。

### 4.3 队列调度

- 按父分支轮转，同一分支内 FIFO；新启动与恢复执行共享公平策略，防止一个循环派单的父代理垄断容量。
- 只有可运行任务参与选取。预算预留暂不可用、provider 冷却、依赖未满足的任务保留具体等待原因，不挡住其他可运行任务。
- 运行任务在模型/工具结算后的安全边界检查调度压力；有竞争分支时让出并重新就绪。不能抢占未结算的模型请求或任意杀掉正在执行的工具来满足时间片。
- 一个已接受的恢复任务不会被无限后来的新任务插队。长工具无法安全抢占时，不承诺严格的秒级公平。
- FIFO 之外的排序来自 runtime，不让模型自报“最高优先级”。恢复队列有老化规则，避免一类任务持续压制另一类。
- provider 的 429 等按已知限流信号退避，记录 `provider_rate_limit`。32 保持为配置容量，实际利用率如实显示，不要求始终占满。

## 5. 嵌套等待与执行名额

父子身份、依赖等待和执行 lease 分开记录。任务状态至少能表达：

| 状态 | 占执行名额 | 行为 |
|---|---|---|
| queued / ready | 否 | 等待首次准入或恢复准入 |
| starting / running | 是 | 可以启动、请求模型或执行工具 |
| waiting_children / waiting_input / waiting_budget | 否 | 已完成安全边界持久化，等待条件满足 |
| stopping | 直到实际执行静默 | 取消已发出，不等于资源已释放 |
| completed / failed / cancelled | 否 | 已结算并确认执行结束 |
| indeterminate | 未确认停止的资源继续隔离占用 | 保存不确定事实，等待 worker/进程核对；不自动重跑 |

父代理调用 `task_wait` 等待子任务时：

1. 结算已经开始的工具和模型请求，提交可恢复的对话边界及依赖关系。
2. 释放父代理执行 lease，保留任务身份、等待订阅和取消控制。已无在途调用的短期预算预留返还；已产生的消耗不返还。
3. 子任务完成、等待超时或用户输入到达时，父代理变为 ready，进入恢复队列。
4. **重新取得执行名额后**才能开始下一次模型请求或工具执行，不能在唤醒回调里绕过配额。

例：32 个子代理各自提交一个后代并等待。32 个父代理到安全边界后释放名额，后代逐步执行；完成后父代理重新排队整合。在不提高 32 的条件下也能推进。

新建父子身份必须形成树；等待依赖另行校验，不允许等待自身、祖先或形成依赖环。语义上的反复转交工作通过祖先任务摘要、预算和重复委派检测限制，不能声称对自然语言任务做完备循环检测。

模型响应结束不自动释放仍在执行的 shell 进程资源。长命令让出前台后由 TerminalService 和进程 lease 管理；需要等待其结果的 agent 按同样的安全边界挂起。单纯执行 `sleep` 不会被识别成可释放容量的子任务等待。

## 6. 预算、期限与取消

### 6.1 整树预算闭环

沿用现有预算类型和账本，增加持久子预留，所有子任务从同一个根预算派生，Workflow 不产生独立的无限额度。

- 入队不为每个任务预留一整份长期执行预算，避免 256 个排队任务锁死资金；执行准入和每次模型调用前按有限额度预留。
- 预算判定使用“已结算消耗 + 所有在途预留”；启动和恢复都不得绕过。预留、返还和结算有 attempt/request 身份，重放不重复扣款。
- 若预算只是被其他在途请求暂时预留，等待其结算；若已确定耗尽，产生明确的 budget stop，不作为普通容量队列无限等待。
- 父级保留收尾额度。有限费用预算下，默认将本次操作额度的 10% 留给根代理整合，可配置；其余共享按需使用，不固定切成 32 份。极小预算不足一次可执行调用时停止并解释，不能制造可用额度。
- 已完成、失败、取消和恢复路径均结算实际使用量。根显示自身与后代消耗的分项及合计，不能先合并子总量再把相同明细重复相加。
- 输入 token、输出 token、缓存命中、工具次数、模型耗时、排队耗时分别记录；上下文占用不冒充累计消耗，未知实际费用明确标记。
- 请求执行前需要可执行的有限计费上界；以输入和最大输出估算时不预设缓存命中。供应商无法提供足够约束或用量缺失时保持未结算/保守预留状态，不伪报精确硬预算。

只有持久预留和恢复结算验收通过后，才解除当前“有费用预算时拒绝 async”的保护。目标协议统一，实施期间不以删掉保护代替闭环。

### 6.2 三种时间分别处理

- `task_wait.timeout_ms`：一次观察等待多久返回，默认 30 秒、最大 60 秒；结束等待不取消任务。
- 任务 `deadline_at`：可选的绝对截止时间，默认无；包含排队和挂起时间，恢复后不重置，后代不能突破祖先期限。到期即请求停止，完成状态须等待执行静默，不能保证不可中断外部操作瞬间终止。
- 运行耗时、排队耗时和挂起耗时：用于统计及明确的预算维度。不能把一个 wall-time 字段在恢复时改成只算 CPU/活跃时间。

通用子任务仍没有隐式硬超时。内置只读角色有单独的证据收敛协议：达到 6 个模型回合或 8 次已开始的工具调用后，runtime 关闭未开始的同批调用，在安全检查点追加最终报告请求，并执行一次无工具、最多 1024 token 的总结。该总结有 90 秒总截止时间；即使上游持续发送 SSE 思考片段，也必须返回完整或明确的 `partial` 终态。父任务同时明确写出“只读”与“禁止修改”且直属子任务已经全部终结时，也进入同一汇总阶段。这个保护不应用于调研后还要修改代码的任务。

### 6.3 取消与故障恢复

取消根任务时原子设置取消 epoch，排队子任务直接取消，活动后代收到停止信号；派发事务必须再次验证取消 epoch。已停止任务不会因完成通知或队列唤醒而复活。

运行资源只在确认执行结束后释放。owner 失联或 lease 到期触发核对/停止旧 worker，不能直接认为 OS 进程已死并让替代进程越额启动。无法确认的外部副作用保留 indeterminate 和必要的容量隔离。

重启时从 TaskRegistry 重建队列，保持提交顺序、任务身份、预算预留、owner 和 attempt；已接受的恢复任务不受新配置较低队列上限驱逐。下调 `max_running` 时停止新派发，待现有执行自然降到上限，不为立即达到数值强杀任务。

## 7. 模型工具与用户体验

保留 `subagent` 作为提交入口，移除 sync/async 两套启动协议。提交快速返回 task_id 和当时状态，需要结果时调用共享 `task_wait`。极短任务已完成时可直接附结果。

统一任务控制工具：`task_list`、`task_wait`、`task_read_output`、`task_stop`；子代理的运行中指导保留 `subagent_message`，completed 任务通过明确 continuation 创建新 attempt。删除重复的 `subagent_status` 模型入口；进度、usage、结果和 continuation 元数据由统一任务接口提供。消息、停止、观察不需要抢占 agent 执行名额。

`task_wait` 支持一或多项任务、游标及 any/all 条件，通知任务变化或完成；等待者取消只移除订阅，显式 task_stop 才停止目标。它同时服务命令任务和子代理。

TUI 展示 `运行 32/32 · 排队 18 · 等待子任务 4`，详情解释排队原因、父任务、角色、最后进度、累计使用量、结果是否已送达。公平队列的位置是近似信息，不伪造预计完成时间。

完成结果用 `(task_id, attempt_id, result_revision)` 进入持久 outbox；父对话摄入与确认可恢复、可去重。崩溃前已领取但未摄入的通知仍可重送，不用“先标已交付再注入”承担丢失窗口。子代理报告保持其来源等级，不当成用户指令。

主代理结束前必须处理当前目标所依赖的结果，或明确报告失败、取消、等待或部分完成。无关历史任务不阻止当前回复。

一个命名分支只提交一次。完整、部分、失败和不确定结果都由父代理整合；除非结果暴露出一个新的、独立且阻塞当前任务的问题，不为同一分支启动替代子任务。对明确只读的委派调查，全部直属孩子交付后由 runtime 禁用父代理工具并要求汇总，防止父代理重新读取孩子已经覆盖的仓库范围。

命令工具继续采用增强后的 `bash` 单一启动入口和 TerminalService；本方案只统一任务身份、控制面、所有权和交付，agent 执行名额与 shell 进程配额仍分别计量。

## 8. 其余能力的取舍

| 方向 | 决策 |
|---|---|
| 委派策略 | 目标默认 adaptive；按任务依赖拆分，不以固定数量或调用率作成功指标 |
| 角色 | 保留当前六种角色及自定义目录；explorer 只读能力继续由 runtime 强制 |
| 上下文 | fresh 默认；再提供可追溯的有限历史继承/fork，保留工具调用配对和明确子目标 |

| 嵌套 | 先保持默认深度 2，打通被授权角色的委派工具与 runtime 门禁；提高深度留到评测后 |

| 结果复用 | 优先 continuation 和带来源的调查产物；暂不做“相同 prompt 即命中”的最终结果缓存 |

## 10. 验收场景

1. **容量与排队**：同时提交 100 个阻塞在测试屏障上的任务，准确出现 32 个执行 lease 和 68 个新任务排队记录；释放一个屏障，只补一个执行名额；全部最终完成。
2. **混合入口**：普通提交、Workflow、UI continue、恢复与嵌套同时竞争，执行 lease 总量始终不超过 32；根会话独立，宿主限制来源可见。
3. **无嵌套死锁**：32 个运行父代理各提交后代并等待，检查挂起检查点、父名额释放、后代完成、父重新准入和最终整合。
4. **公平性**：A 分支持续派单，B 分支和已就绪父代理不会被后来的 A 无限插队；provider 阻塞任务不造成队头阻塞。
5. **背压**：排满新任务队列/存活数量，新增提交明确未接受；已有任务仍可取消、等待、让出和恢复，无孤儿任务。
6. **预算**：32 路调用同时预留，已消耗加在途预留不突破有效额度；失败、取消、超时、缺失用量与断点恢复不重复结算。
7. **故障注入**：在入队、lease 提交、进程启动、worker 回执、工具副作用、结算、通知领取、父摄入各边界杀 owner；核对不重复执行、不遗失结果、不凭失联释放占用。
8. **时间与取消**：wait 超时任务继续运行；排队 deadline 到期不启动；取消与派发竞争无复活；停止中资源未静默前不被复用。
9. **资源驻留**：256 个排队任务不启动 worker；安全挂起释放 execution lease。活动 RuntimeThread 在透明重载接通前保持可继续，不能为了降低驻留破坏 UI continue；终态历史和嵌套结果受明确生命周期边界限制。
10. **真实效果**：固定源码、模型、权限和预算，对多模块修复、跨仓调查、独立测试、单文件小改动比较旧基线和新方案，分别记录冷/热缓存、全树费用、重复阅读、首派延迟与结果质量。不把“用了更多子代理”当成通过标准。
