# Orca v0.5.3

Fixes after v0.5.2:
- An edit or write that succeeds no longer fails the turn when the model is
  DeepSeek.
- Approval prompts for DeepSeek tool calls appear again.

## Changes

### DeepSeek tool calls

- DeepSeek sends a tool call as a name and arguments, and Orca recorded every
  such call as a read. Since v0.5.1 a completed edit or write carries its
  diff, and the runtime takes a diff only from a write, so every successful
  edit or write failed the turn with an `IllegalTransition` error after the
  file had already changed. Orca now records each call as the kind of tool it
  is: an edit or write as a write, a shell command as a shell command.
- Edit and write rows show their diff, and a shell command's result keeps its
  exit code.
- ACP clients see the kind of each tool call, such as edit or execute,
  instead of read.
- Sessions from v0.5.1 and v0.5.2 still resume. A tool call waiting for
  approval still matches the call the session recorded, and an edit that
  session recorded as a read completes without its diff instead of failing
  the turn.

### Approvals

- Since v0.5.1 the approval check compared the call the runtime recorded,
  whose target comes from the arguments, with the call as DeepSeek sent it,
  with no target. They never matched, so the approval prompt for a DeepSeek
  call never appeared. The check now reads the call's action and target the
  way the runtime records them.

### Tests

- The mock provider sends its `edit` call the way DeepSeek does, as a read
  with no target, so the tests exercise what a real session sends.

## Compatibility

- Sessions from v0.5.1 and v0.5.2 open and resume. An edit those versions
  recorded as a read shows no diff if it completes after the upgrade.
- ACP clients and the task list now see a DeepSeek shell command or edit as
  such, where they used to see a read.

Existing configurations and conversation history remain readable.
