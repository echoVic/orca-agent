# Orca v0.5.23

`run_script` now runs inside Orca, in an embedded JavaScript engine, and no longer needs Node.js. Calls a script starts together run at the same time, the terminal UI shows the script the model wrote and what each of its calls did, and that record is saved with the session. The tool is still experimental and off by default: a second comparison with it on and off showed neither a saving nor a cost.

## Changes

- **`run_script` runs in process.** A script used to run in a Node.js process of its own. It now runs in a QuickJS engine (QuickJS-NG through `rquickjs` 0.14) created inside Orca for each script and dropped after it, so the tool works on a machine without Node.js and a script starts with no process to launch. The engine has no file, network, process or timer API; a script still reaches the outside only through `tools.read_file`, `tools.glob`, `tools.grep` and `tools.git_status`, and each call is still checked by the runtime (the four-name list, the read-only check, the tool's schema, the `PreToolUse` hook) and run under the read-only profile. On `aarch64-apple-darwin` the release binary grows by 1,019,360 bytes (71,348,400 to 72,367,760).
- **Calls started together run together.** Calls a script starts before it awaits, as with `Promise.all`, are one batch. The runtime checks them one by one in the order they were started, runs every `PreToolUse` hook of the batch before any call of it, and then runs the calls at the same time, up to `tools.max_read_parallel` (8 by default). Answers go back in start order. The tool's description tells the model so.
- **Limits.** `[tools.script] memory_limit_mb` (64 by default, never less than 8) is new: a script that would hold more fails with `the script used more than 64 MiB`. `timeout_secs` (60) and `max_tool_calls` (100) are unchanged, and `timeout_secs` is now held between one second and one day. The arguments of calls waiting to be answered may hold 256 KiB of text in all, and 1000 calls may wait at once; a script past either is told to await some calls first. The script's own call stack is limited, and a script that recurses without end fails with QuickJS's `RangeError: Maximum call stack size exceeded`.
- **When a script's time is up.** The calls it has running are stopped and the calls it has not started are not started; a `PreToolUse` hook already running for one of them finishes first. `grep`, `glob` and `git_status` now stop when asked, as `read_file` did: `grep` and `git_status` end the `rg` or `git` they started, and `glob` stops walking. The same holds when the model calls them directly, so a cancelled turn no longer waits for a search to finish; the call ends as cancelled, with `grep was cancelled`, `glob was cancelled` or `git_status was cancelled`.
- **A script that cannot be stopped.** QuickJS asks whether to stop between the steps of a script and inside a regular-expression match, but not inside every built-in operation that loops on its own: reversing an object that claims to hold 2^53 items never asks. Such a script is stopped on time like any other and the turn goes on, but the operation keeps a CPU core busy, and the script's memory, until it finishes or Orca exits. While two such scripts are still running in an Orca process, `run_script` refuses to start another there and says why.
- **Seeing a run in the terminal UI.** A `run_script` row opens with a click or ctrl+o and shows three sections: `Script`, the script the model wrote, with line numbers; `Calls`, one entry per call with its arguments, how it ended, how long it took, the size of what came back and its first lines, with `┬ ├ └` joining the calls of one batch; and `Returned to the model`, or `Failed` with the error. The calls appear when the script ends, and the row's first line then ends with the number of calls and the time the run took. The model still receives only what the script returned.
- **A run's calls are saved with the session.** What `run_script` wrote of its calls is recorded with its result, so the row shows them after `orca --resume`, after switching back from a side conversation (`/side`) or an agent's conversation, and in a session attached while the script ran. A script that makes all 100 calls it is allowed adds about 130 KiB to its session file, and no script adds more than about 256 KiB: one allowed many more calls keeps the first of them and a line saying how many were left out. A row says `Calls were not recorded for this run` for a script run by an earlier version and for a result Orca wrote itself after an interruption. A script in a turn Orca starts from a message queued behind another turn shows its calls as they happen, but that turn is not recorded this way and its calls are not kept.
- **`/scripts`.** A new slash command prints whether `run_script` is on, its limits, the tools a script can call, and the description and parameter schema the model is sent for the tool, read from the tool registry.
- **The output stream of a script.** `orca exec` in text mode and `tool.output.delta` in JSONL carry the same text the terminal UI arranges. Each call is now a summary line, `  2 ┬ read_file {"path":"a.rs"} · ok · 3ms · 1.2 KiB`, followed by up to five lines of what came back, indented by ten spaces and cut at 120 characters and 400 bytes, and the last line carries the run's time: `4 tool calls · 412ms`. Control characters and the characters that set the direction text is drawn in are written as `�`, and a tab as the spaces to the next tab stop. An ACP client receives the same text as one in-progress update of the tool call just before the completed one.

## Measurement

Five repository questions, three runs each way, through `orca exec` against the real provider on 2026-11-19. All 30 runs ended normally.

| | `run_script` off | `run_script` on |
|---|---|---|
| Runs | 15 | 15 |
| Answers right | 15 | 15 |
| Model rounds | 53 | 57 |
| Cost (USD) | 0.018668 | 0.017745 |

With the tool on, the model called it in 3 of the 15 runs (5 calls in all), and the runs that used it took no fewer rounds. Four of the tasks took two to four rounds and the fifth five to eight, which leaves a script little to save, and 53 rounds against 57 is within the spread between runs of the same task. The comparison shows neither a saving nor a cost, so `enabled` stays `false` by default.

## Compatibility

- **Node.js is no longer used by `run_script`.** With `enabled = true` the tool is advertised whether or not Node.js is installed. Workflows still use Node.js as before.
- **What a script can do has changed in one way.** `eval` and `Function` exist in a script, where the Node.js host disabled code generation from strings. They give a script nothing it did not have: the engine holds no API beyond the language's own and the four `tools` functions. There are still no timers, and `queueMicrotask` is absent. A script that relied on V8-specific behaviour, such as the exact text of an error's stack, may behave differently.
- **Hooks.** A `PreToolUse` hook still runs once for each call a script makes and may rewrite or block it. For a batch, every hook of the batch now runs before the first call of the batch, where each used to run just before its own call.
- **Consumers of the output stream.** A program that counted a script's calls by lines containing ` · ` must count summary lines only; `scripts/eval/code_mode/run.py` does. No event field is added, renamed or removed.
- **Session files.** A `run_script` result is preceded in its recorded commit by the tool's output, using a patch (`OutputDelta`) and a field (`streamed_output`) the format already had, so earlier versions read these sessions and the runtime-surface contract is unchanged.
- **Cancelling a search.** A direct `grep`, `glob` or `git_status` that is cancelled now returns a cancelled result at once where it used to finish first.
- **Configuration.** The only new key is `[tools.script] memory_limit_mb`. The script host module and its entry in the Windows platform contract are removed.

## Verification

Release gates run with framework retries disabled. Linux and native Windows x64/ARM64 checks must pass on the final main commit before the tag is pushed. This is the first release whose Windows builds compile the embedded C engine, so the Windows jobs on that commit are the first evidence that it builds and that the engine's tests pass there.

The changes ship with engine contract tests (scripts that return, log, fail and call tools; batches and their order; the wall clock, the cancel, the memory limit met at once and in small pieces, the stack limit, a regular expression that backtracks without end, native loops that are left behind and counted, a script that leaves the function it is the body of, and scripts that replace `Promise`, `JSON` and `Object.prototype` members), runtime tests for the checks, the limits, parallel batches and the output format, tool tests for cancelling `grep`, `glob` and `git_status`, terminal UI tests for the row, the rebuilt row and `/scripts`, and a real run that was resumed to confirm its calls were read back from the session file.
