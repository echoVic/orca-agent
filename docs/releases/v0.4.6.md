# Orca v0.4.6

Security architecture release: capability resolution and process execution now
fail closed at the runtime boundary.

## Capability Kernel

- Add immutable `CapabilityRequest`, `EffectiveCapability`, and
  `CapabilityReceipt` contracts with final capability bits, Plan read-only
  ceilings, and child-agent subset checks.
- Keep `UserTrustedIntegration` behind an explicit user-owned launcher; a
  model/tool request cannot self-declare the advisory trusted class.
- Route runtime shell and MCP stdio process launches through
  `ExecutionBroker`; advisory/unavailable sandbox states cannot silently run a
  non-dangerous command.
- Require explicit MCP capabilities in user-owned configuration, defaulting to
  read-only.
- Persist workflow capability grants in the launch record and carry them
  through restart; hooks use the run's bounded capability ceiling.

## Path and Sandbox Boundaries

- Canonicalize and contain command cwd values under a `WorkspaceIdentity`, with
  Unix root replacement detection using device/inode identity.
- Open Linux Landlock roots as descriptor-backed rules and authorize native
  Windows AppContainer/ConPTY launches through the broker before handle-based
  spawning.
- Reject relative and `..` traversal paths during capability resolution.
- Remove the Linux plain-shell fallback and reject unsupported external
  sandbox policies.
- Require full Landlock/seccomp enforcement for workspace-write, not only
  restricted read profiles.
- Remove Seatbelt workspace-write global reads; only platform and configured
  roots are readable.
- Treat stderr denial text as explanatory diagnostics only. Permission prompts
  require a structured backend denial receipt.

## Configuration and Protocol

- Project `.orca/config.toml` cannot override user execution mode, permission
  rules/profiles, MCP servers, hooks, external tools, subagents, workflows,
  tools, or budgets.
- Permission events expose the command, cwd, capability roots, network posture,
  backend, and enforcement state.
- Retry authority fingerprints include effective settings and the tool catalog;
  profile, root, network, and approval changes invalidate older grants.
- Direct `ProcessJob::spawn` is deprecated and denied in the core/runtime/tool/
  TUI/MCP crates; production launches must use `ExecutionBroker`.

## Compatibility

This release intentionally removes the old optional runtime-config and
stderr-driven filesystem/unsandboxed retry paths. Existing project files that
set execution capabilities must move those settings to user-owned config.
