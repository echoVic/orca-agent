# Orca v0.4.29

Inline structured questions, persistent model preferences, truthful Full
Access transitions, and deterministic release validation.

This release supersedes the unpublished `v0.4.28` tag.

## Changes

- Replaces the modal `ask_user_question` flow with a capability-driven inline
  questionnaire in the composer area. One request can contain one to four
  questions with paging, single-select, multi-select, previews, custom answers,
  and a typed Chat response.
- Preserves questionnaire state through submission acknowledgement and failure,
  and carries structured answers through the runtime surface, ACP, JSONL, and
  durable continuation capsules while retaining compatibility with legacy
  single-question and capsule formats.
- Saves model and reasoning-effort changes from `/model` and `/config` to the
  user `config.toml` without persisting approval mode. Existing comments and
  unrelated configuration remain intact.
- Makes `full-auto` a real Full Access transition. The TUI asks for explicit
  confirmation, the runtime atomically commits `FullAuto` and `TrustedHost`,
  clears restrictive active profiles, and applies `DangerFullAccess` to the
  active task's next tool admission.
- Keeps already running tools and existing delegated children on their
  immutable policy snapshots. New child delegations inherit the committed Full
  Access policy.
- Adds effective execution profile, resolved shell sandbox, and active
  permission profile to `/status`, and includes the same context in sandbox
  launch and denial diagnostics.
- Tightens questionnaire layout for terminal character widths, including
  navigation marker spacing, aligned option descriptions, non-duplicated
  headings, and option-count-aware footer hints.
- Isolates the workflow cancellation checkpoint contract in the two-thread CI
  profile and keeps its fixture focused on the workflow worker rather than an
  unrelated nested agent lifecycle, so release validation remains
  deterministic under runner load.

## Compatibility

Existing three-field TUI settings intents remain readable. Full Access widening
requires the new explicit confirmation marker and dedicated runtime patch.

Durable user-input capsules v1 and v2 remain readable alongside v3. Existing
delegated children are not widened when a parent switches modes; only child
work created after the committed transition inherits `TrustedHost`.

Approval mode remains session-scoped and is not written to the user
configuration.
