### 唯一的红点：`linux_shell_probe.py`

```
alpine:latest            state=completed  exit=0     ''
debian:bookworm-slim     state=None       exit=None  ''
verdict: FAIL
```

`debian:bookworm-slim` 里 `orca exec` 直接失败，原始错误：

```
DeepSeek provider error: failed to build streaming HTTP client: builder error:
unexpected error: No CA certificates were loaded from the system; install the ca-certificates package
```

这是本轮之前有意做的变更，不是回归缺陷：

- `9347cd30` 迁移到 reqwest 0.13，只用系统信任库（不再编译内置根证书）
- `b35560b8` 把「没有系统 CA」从 panic 改成显式错误
- `61ab4e1d` 记录 Orca 对 CA bundle 的要求
- `95d258ee` 在 TB2 adapter 里随二进制发 certifi bundle（本轮 TB2 因此不受影响）

`linux_shell_probe.py` 提交于这次迁移之前，仍在断言「裸 debian-slim 容器里 `orca exec` 能跑」。
它测的是 BusyBox/dash 的 shell 契约，现在实际测到的是 CA 策略。修法二选一：镜像里装
`ca-certificates`，或按新契约断言这条显式错误。注意纯 `http://` 端点也一样失败——没有信任库时
连客户端都不建。

## 发现

### 1. #114 类问题没有修完：包裹 shell 的 argv 仍带着整段指令

`install-windows-3-11` 本轮记 `NonZeroAgentExitCodeError`（exit 143）。轨迹显示 agent 在 turn 内跑了：

```
kill $(cat /app/vm/test.pid) 2>/dev/null; sleep 2; pkill -f "win311.img" 2>/dev/null; ...
```

该工具调用自身就以 `status=failed exit=143` 结束（`pkill -f` 匹配到了执行它的 shell 自己的命令行），
随后 agent 仍在继续生成，但整个 trial 在此时终止、验证器以 0 分收尾（2 passed / 2 failed，
QEMU 已在跑，缺的是 VNC/键盘那两项）。

上一轮 #114 的修法是把指令从 `orca` 的 argv 挪到 stdin：

```
printf '%s' '<instruction>' | orca exec --mode full-auto --output-format jsonl
```

但这条命令是 Harbor 用 `sh -c` 执行的，`sh` 自己的 argv 里仍然完整包含指令文本，
而这条指令里就有 `/app/isos/win311.img`。于是同一个 `pkill -f "win311.img"` 不但打死 agent 自己的
shell，也打死了 Harbor 的包裹 shell —— trial 直接以 143 结束，而不是让 agent 继续。

影响：任何 agent 会按进程名/命令行做清理、且模式能匹配到自己指令里 token 的题目，都可能这样丢分。

建议：让指令不出现在任何进程的 argv 里。例如 adapter 把指令写进容器内的文件后用
`orca exec < /tmp/instruction.txt`，或经 Harbor 的 exec 环境变量传递（`printf '%s' "$ORCA_INSTRUCTION"`），
两者都不会被 `pgrep -f` / `pkill -f` 匹配到。

### 2. L1 有两条过期的契约断言

- `linux_shell_probe.py`：见上，断言早于 reqwest 0.13 的 CA 策略。
- `exit_code_probe.py` 的 approval 用例把失败标注为 `blocked by #85`，但 #85 是
  「`orca workflow source <name>` 忽略 `ORCA_HOME`」，已关闭且与审批无关。注解是错的，
  会误导下一轮 triage。

### 3. 本地旧检出（`baa30dab`）上的审批契约失败 —— 已在上游修复

在本轮换到 v0.5.10 之前，先在本地 `master`（`baa30dab`，v0.5.0 + 41 commits）上跑过一次 L1：
26 个 run 里 25 绿，唯一红点是 `exit_code_probe.py` 的
`denied action in jsonl → 3 / approval_required`（实测 `exit=0 status=success`）。

复现与根因：suggest 模式下需要审批的 shell 调用先发 `approval.requested`，紧接着 fence 抛
`tool interaction differs from the committed provider request`，工具调用被记为错误，会话以
`success`/exit 0 结束——无头调用方会把「等待审批」当成「任务成功」。上游 `62bd258e`
（2026-09-28，*fix(runtime): record a DeepSeek tool call as the tool it is*）的提交信息正好写明：
「approval check 仍把 surface 请求与 provider 原样发来的调用（无 target）比较，所以 DeepSeek 调用的
审批提示从未出现」。用本机安装的 0.5.10 复跑同一场景得 `exit=3 / approval_required`，v0.5.10 上
`exit_code_probe.py` 6/6 通过。
