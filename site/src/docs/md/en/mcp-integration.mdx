# MCP Integration

Add MCP servers with `orca mcp add`, inspect them with `orca mcp list` and
`orca mcp get`, remove them with `orca mcp remove`, and log in to or out of a
remote server's OAuth with `orca mcp login`/`orca mcp logout`. These commands
only write the user-owned Orca configuration (and, for `login`/`logout`, the
credential store next to it); a project's `.orca/config.toml` is never
touched, and a change takes effect the next time a session starts. See
the [CLI reference](cli-reference.md#orca-mcp) for the full option list.

The user configuration is $ORCA_HOME/config.toml when ORCA_HOME is set,
otherwise ~/.orca/config.toml.

## Stdio server

~~~bash
orca mcp add repository -- node /absolute/path/to/server.mjs
~~~

## Remote server (HTTP or SSE)

~~~bash
orca mcp add docs --url https://mcp.example.test/mcp \
  --header "Authorization: Bearer token-from-environment"
~~~

A stdio server needs a command; a remote server needs a url. Keep
credentials in the environment where possible: `--bearer-token-env-var` names
an environment variable read at connect time instead of storing a token in
the config file.

`orca mcp add` does not set capabilities, timeouts, or
[tool filters](#tool-filters). A new server defaults to a read-only capability
set; grant only what the integration needs by editing the entry
`orca mcp add` created:

~~~toml
[[mcp_servers]]
name = "repository"
transport = "stdio"
command = "node"
args = ["/absolute/path/to/server.mjs"]
startup_timeout_ms = 10000
tool_timeout_ms = 30000

[mcp_servers.capabilities]
read = true
write = false
metadata_write = false
network = false
shell = false
agent = false
~~~

## Remote servers and login

`--transport` selects `http` (streamable HTTP, the default) or `sse`. `http`
speaks the current MCP transport: every request is a POST, and the session id
and protocol version the server negotiated at `initialize` travel with each
later request. `sse` starts the same way, and falls back to the legacy
HTTP+SSE transport only when the server answers that first `initialize` POST
with 400, 404, or 405: a GET then opens an event stream, and requests are
POSTed to the address it hands back. Existing `sse` servers keep working, and
`--transport sse` suits a server that may speak only the legacy transport.

A remote server authenticates one of three ways:

- **A static header** — `--header "Authorization: ..."`, sent on every
  request.
- **`--bearer-token-env-var VAR`** — `orca` reads `VAR` from its own
  environment at connect time and sends it as a bearer token. The token
  itself is never written to the config file.
- **OAuth**, for a server configured with neither of the above. Run
  `orca mcp login <name>` to authorize it in your browser; the authorization
  url is also printed, for a machine with no browser to open it by hand.
  `orca mcp logout <name>` deletes the saved login. `login` refuses a stdio
  server, or one already using a static header or `--bearer-token-env-var`,
  since neither uses OAuth.

The options are saved as keys of the server's entry, which you can also
write by hand:

~~~toml
[[mcp_servers]]
name = "search"
transport = "http"
url = "https://search.example.test/mcp"
bearer_token_env_var = "SEARCH_TOKEN"   # --bearer-token-env-var

[[mcp_servers]]
name = "tracker"
transport = "http"
url = "https://tracker.example.test/mcp"
oauth_client_id = "orca-cli"            # --client-id
oauth_callback_port = 51000             # --callback-port
~~~

`oauth_client_id` is a client id the authorization server issued ahead of
time; without one, Orca registers itself with the server. `oauth_callback_port`
fixes the port of the address the browser comes back to,
`http://127.0.0.1:<port>/callback`, for a server that only accepts a
redirect address registered in advance; otherwise any free port is used.

OAuth tokens are stored in `$ORCA_HOME/mcp-credentials.json`, next to
`config.toml` and readable only by its owner, keyed by server name and url —
moving a server to a new url invalidates the login saved under the old one.
`orca mcp list` and `orca mcp get` show each server's auth status
(`oauth: logged in`, `oauth: not logged in`, `bearer: $VAR`, `static header`,
or `-` for a stdio server) without ever printing the token itself.

When a saved login stops working during a session and cannot be refreshed,
the tool call fails with this error:

~~~text
MCP server requires login: run 'orca mcp login <name>', or log in from /mcp
~~~

`/mcp` then shows the server as `needs login` right away: a server's status
there updates as soon as it changes, while a turn runs too.

`login` and `logout` only change configuration or the credential store; they
never touch a session that is already running. A running TUI session picks
up the change by reconnecting the server from the `/mcp` panel.

## When servers connect

A session's servers connect in the background, all at once, as the session
starts: the interactive TUI starts a new conversation's servers as soon as
it opens, before your first message, or, on a first run in a folder, once
you have reviewed the workspace (and entered an API key, when none is set).
An enabled server is `starting` until it connects, fails, or
turns out to need a login (a disabled one is listed as `disabled` and never
connected), and each request it is sent while connecting
(`initialize`, `tools/list`, `prompts/list`) is bounded by its
`startup_timeout_ms`, 30 seconds unless set. A turn waits, before its first
model request, only for the servers still connecting, so the model is
offered every tool they bring; the TUI's status line says
`connecting MCP servers` meanwhile, and `Esc` interrupts the turn, wait
included. The conversation your first message starts in the TUI takes over
the servers as they stand, connected or still connecting, rather than
connecting them again. Quitting stops every stdio server, those still
connecting too, and so does `Ctrl+C` while `orca exec` waits for them.

## Manage servers in the TUI

In the interactive TUI, `/mcp` lists the conversation's servers and how each
stands: connected, with its tool count; failed, with the reason; needing a
login; or disabled. `Enter` shows a server's tools, each with the name a
permission rule uses for it, marked `read-only` in front when the server
says so; its prompts with their arguments; why its prompts could not be
listed, when `prompts/list` failed (`prompts unavailable: <reason>`); and
the `enabled_tools`/`disabled_tools` its configuration sets. `r` reconnects
the selected server, `l` logs in to it with OAuth and then reconnects it, and
`o` deletes its saved login and then reconnects it. While a login waits for
the browser, `l` again cancels it: it stops waiting at once and frees the
callback port. Once the browser is back with the code, the login finishes
and `l` no longer cancels it. All of this works before your first message
too: the servers are connecting by then, and a
login there reconnects the server the conversation then keeps. `/mcp` lists
the servers of the configuration Orca started with: one added while the TUI
is open appears after you restart it. See
[Terminal UI](terminal-ui.md#mcp-servers) for the panel and its keys.

## Prompts

A server that declares the `prompts` capability has its prompts listed when
it connects, and again when it reconnects; `/mcp` shows them in the server's
details. In the TUI each prompt is a slash command named like the server's
tools, `/mcp__<server>__<prompt>`, followed by the prompt's arguments in
order: `/mcp__github__review_pr 123 main`. The last argument takes the rest
of the text, and a missing required argument shows the usage instead of
running anything. Orca asks the server for the prompt (`prompts/get`) and
sends what it returns as your message: its text parts joined by blank lines,
the text of any embedded resource, and its images as attachments. When the
server reports an error, the conversation says so and nothing is sent.
`Esc` cancels a prompt the server has not answered yet: what it returns is
dropped, though its request runs to its end on the server. A prompt can run
before your first message: what it returns is that message, and starts the
conversation. See
[Terminal UI](terminal-ui.md#mcp-prompts) for the argument rules and limits.

## Resources

A server that declares the `resources` capability lets the model look at what
it holds, through the read-only tools `list_mcp_resources`,
`list_mcp_resource_templates`, and `read_mcp_resource`. The two list tools take
an optional `server` name and answer with the same JSON object whether or not
one is given: `{"resources": [...], "errors": [...]}`, with `resourceTemplates`
in place of `resources` for templates. Without `server` they cover every server
that declares resources: a server that failed to start or to list is named in
`errors`, and the others are still listed. With `server`, a server that is not
connected, or whose list request fails, fails the call with its error instead.

A server's list is read a page at a time, up to 100 pages. A list that is cut
short, because it has more pages than that or because the server names a
cursor it has named before, keeps the entries read so far, and `errors` has a
line for it that names the server and says why it stopped, so the model does
not take the list for everything the server has:

~~~text
<server>: MCP list stopped after 100 pages
<server>: MCP server repeated a list cursor
~~~

## Images from tools

`deepseek-flash` and `auto`, which uses it, are the only models that see the
images an MCP tool returns, inline on the tool message. `deepseek-v4-pro` and
custom models, even ones declared with `supports_images = true`, get a note in
their place saying the model cannot see them. Only PNG, JPEG, GIF, and WebP are
accepted, decoded size up to 5 MiB each; anything else is dropped with a note
explaining why. One MCP response, images included, is limited to 16 MiB; a
larger one fails the call.

Each request carries at most the 3 newest tool images in the conversation;
older ones are replaced with a note. This limits what goes out over the wire
only — the full history stays on disk.

Resuming a session does not reload earlier tool images, regardless of which
model resumes it. The resumed conversation keeps the note in their place.

## Read-only tools

A server can mark a tool read-only in its `tools/list` response
(`readOnlyHint`). Orca then treats a call to that tool as a read:

- Suggest mode does not ask before the call; plan mode allows it, while
  every other MCP tool call is still denied.
- Whether a tool is read-only is entirely up to the server's own
  declaration.
- A tool the server also marks `destructiveHint` is still asked about,
  the same as any other write.

## Tool filters

A server's entry can limit which of its tools Orca registers. `orca mcp add`
does not set the two keys, so write them by hand. Both take the names the
server gives its tools in `tools/list`, such as `createIssue`, not Orca's
`mcp__github__createissue`:

~~~toml
[[mcp_servers]]
name = "github"
transport = "http"
url = "https://github-mcp.example.test/mcp"
enabled_tools = ["list_issues", "create_issue", "delete_repo"]
disabled_tools = ["delete_repo"]
~~~

- `enabled_tools` is an allow-list: only the tools it names are registered.
  An empty list, `enabled_tools = []`, registers no tool at all.
- `disabled_tools` is a deny-list applied after the allow-list, so a tool on
  both lists is left out. Here only `list_issues` and `create_issue` are
  registered.
- Leave a key out to skip that filter. A tool filtered out is not registered,
  and the model never sees it.

`orca mcp get` shows both keys, `-` for one that is not set and `none` for an
empty list, and so do the server's details in `/mcp`.

## Always allow

An MCP tool's approval panel offers two extra choices beyond the ones every
tool call gets: `5` Always allow `<tool>` (saved) and `6` Always allow the
`<server>` server (saved). Both run the call and, like `3` Allow `<tool>` this
session, stop asking for the rest of the session; they additionally append an
allow rule to the user configuration so a future session skips the prompt
too:

~~~toml
[[permissions.rules]]
tool = "mcp__github__create_issue"
decision = "allow"

[[permissions.rules]]
tool = "mcp__github__*"
decision = "allow"
~~~

The first rule (`5`) names one tool; the second (`6`) covers every tool on
that server. Neither writes a `pattern`: a rule without one covers every call
of its tool, and an MCP call's target is the tool's own name anyway. To write
such a rule by hand, name the tool as Orca does, as the `/mcp` details show
it: lowercase, with every run of other characters turned into `_`. Orca reads
a rule's `mcp__` name the same way, so `mcp__GitHub__createIssue` also names
`mcp__github__createissue`. See
[Permission rules](approval-modes.md#permission-rules). If the rule cannot be
saved (an existing config that fails to parse, for example), the call still
runs and the rest of this session still skips the prompt; the conversation
explains that saving the rule failed.

A call follows the strictest permission rule that matches it, so a `deny` or
`prompt` rule in your configuration that matches the tool still applies in
later sessions, beside the saved allow rule. Orca checks for one when it
saves the rule, matching rules as it does for a call, and the conversation
then says `saved, but a stricter rule in your config still applies to <tool>`.
The call still runs, and the rest of this session still skips the prompt.

## Operate safely

1. Start with a read-only capability set.
2. Use absolute paths for local server programs.
3. Review a workspace before trusting its project configuration.
4. Use orca doctor to validate local configuration and sandbox readiness; it
   is intentionally read-only and does not start MCP servers.
5. Check how each server stands in the TUI's `/mcp` panel, and reconnect it
   there.

`orca mcp list` and `orca mcp get` inspect configured servers without
connecting to them. They print a stdio server's command and arguments and a
remote server's url as configured, so keep secrets out of those; they never
print the values of `env` or `headers`, only their names, or a token. There
is no CLI command to restart, test, or diagnose a running MCP connection: a
running connection belongs to its session, and the TUI's `/mcp` panel shows
its status and reconnects it.
