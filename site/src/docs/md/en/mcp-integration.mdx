# MCP Integration

Add MCP servers with `orca mcp add`, inspect them with `orca mcp list` and
`orca mcp get`, and remove them with `orca mcp remove`. These commands only
write the user-owned Orca configuration; a project's `.orca/config.toml` is
never touched, and a change takes effect the next time a session starts. See
the [CLI reference](cli-reference.md#orca-mcp) for the full option list.

The user configuration is $ORCA_HOME/config.toml when ORCA_HOME is set,
otherwise ~/.orca/config.toml.

## Stdio server

~~~bash
orca mcp add repository -- node /absolute/path/to/server.mjs
~~~

## Remote server (HTTP or SSE)

~~~bash
orca mcp add docs --url https://mcp.example.test/mcp \
  --header "Authorization: Bearer token-from-environment"
~~~

`--transport` selects `http` (the default) or `sse`. A stdio server needs a
command; a remote server needs a url. Keep credentials in the environment
where possible: `--bearer-token-env-var` names an environment variable read
at connect time instead of storing a token in the config file.

`orca mcp add` does not set capabilities, timeouts, or tool filters. A new
server defaults to a read-only capability set; grant only what the
integration needs by editing the entry `orca mcp add` created:

~~~toml
[[mcp_servers]]
name = "repository"
transport = "stdio"
command = "node"
args = ["/absolute/path/to/server.mjs"]
startup_timeout_ms = 10000
tool_timeout_ms = 30000

[mcp_servers.capabilities]
read = true
write = false
metadata_write = false
network = false
shell = false
agent = false
~~~

## Images from tools

`deepseek-flash` and `auto`, which uses it, are the only models that see the
images an MCP tool returns, inline on the tool message. `deepseek-v4-pro` and
custom models, even ones declared with `supports_images = true`, get a note in
their place saying the model cannot see them. Only PNG, JPEG, GIF, and WebP are
accepted, decoded size up to 5 MiB each; anything else is dropped with a note
explaining why. One MCP response, images included, is limited to 16 MiB; a
larger one fails the call.

Each request carries at most the 3 newest tool images in the conversation;
older ones are replaced with a note. This limits what goes out over the wire
only — the full history stays on disk.

Resuming a session does not reload earlier tool images, regardless of which
model resumes it. The resumed conversation keeps the note in their place.

## Read-only tools

A server can mark a tool read-only in its `tools/list` response
(`readOnlyHint`). Orca then treats a call to that tool as a read:

- Suggest mode does not ask before the call; plan mode allows it, while
  every other MCP tool call is still denied.
- Whether a tool is read-only is entirely up to the server's own
  declaration.
- A tool the server also marks `destructiveHint` is still asked about,
  the same as any other write.

## Operate safely

1. Start with a read-only capability set.
2. Use absolute paths for local server programs.
3. Review a workspace before trusting its project configuration.
4. Use orca doctor to validate local configuration and sandbox readiness; it
   is intentionally read-only and does not start MCP servers.
5. Inspect runtime status in the interactive TUI during a live task.

`orca mcp list` and `orca mcp get` inspect configured servers without ever
printing credential values; `env` and `headers` show only the configured key
names. There is still no public CLI command to restart, test, or diagnose a
running MCP connection — that remains part of the running session.
