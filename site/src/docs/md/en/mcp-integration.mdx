# MCP Integration

MCP servers are declared in the user-owned Orca configuration. They are not
managed by a separate public command namespace. Edit the TOML file, review the
server command or endpoint, then launch an interactive or headless task that
uses the configuration.

The user configuration is $ORCA_HOME/config.toml when ORCA_HOME is set,
otherwise ~/.orca/config.toml. A project configuration is considered only after
that workspace is trusted.

## Stdio server

~~~toml
[[mcp_servers]]
name = "repository"
transport = "stdio"
command = "node"
args = ["/absolute/path/to/server.mjs"]
startup_timeout_ms = 10000
tool_timeout_ms = 30000

[mcp_servers.capabilities]
read = true
write = false
metadata_write = false
network = false
shell = false
agent = false
~~~

## SSE server

~~~toml
[[mcp_servers]]
name = "docs"
transport = "sse"
url = "https://mcp.example.test/sse"
headers = { Authorization = "Bearer token-from-environment" }
startup_timeout_ms = 10000
tool_timeout_ms = 30000
~~~

The transport is either stdio or sse. A stdio server needs a command; an SSE
server needs a url. Keep credentials in the environment where possible, and
grant only the capabilities the integration needs.

## Operate safely

1. Start with a read-only capability set.
2. Use absolute paths for local server programs.
3. Review a workspace before trusting its project configuration.
4. Use orca doctor to validate local configuration and sandbox readiness; it
   is intentionally read-only and does not start MCP servers.
5. Inspect runtime status in the interactive TUI during a live task.

There is no public CLI command to list, restart, test, or diagnose individual
MCP servers. Those lifecycle actions remain part of the running session and its
configuration boundary.
