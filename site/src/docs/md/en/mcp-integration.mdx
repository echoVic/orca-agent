# MCP Integration

Add MCP servers with `orca mcp add`, inspect them with `orca mcp list` and
`orca mcp get`, remove them with `orca mcp remove`, and log in to or out of a
remote server's OAuth with `orca mcp login`/`orca mcp logout`. These commands
only write the user-owned Orca configuration (and, for `login`/`logout`, the
credential store next to it); a project's `.orca/config.toml` is never
touched, and a change takes effect the next time a session starts. See
the [CLI reference](cli-reference.md#orca-mcp) for the full option list.

The user configuration is $ORCA_HOME/config.toml when ORCA_HOME is set,
otherwise ~/.orca/config.toml.

## Stdio server

~~~bash
orca mcp add repository -- node /absolute/path/to/server.mjs
~~~

## Remote server (HTTP or SSE)

~~~bash
orca mcp add docs --url https://mcp.example.test/mcp \
  --header "Authorization: Bearer token-from-environment"
~~~

`--transport` selects `http` (the default) or `sse`. A stdio server needs a
command; a remote server needs a url. Keep credentials in the environment
where possible: `--bearer-token-env-var` names an environment variable read
at connect time instead of storing a token in the config file.

`orca mcp add` does not set capabilities, timeouts, or tool filters. A new
server defaults to a read-only capability set; grant only what the
integration needs by editing the entry `orca mcp add` created:

~~~toml
[[mcp_servers]]
name = "repository"
transport = "stdio"
command = "node"
args = ["/absolute/path/to/server.mjs"]
startup_timeout_ms = 10000
tool_timeout_ms = 30000

[mcp_servers.capabilities]
read = true
write = false
metadata_write = false
network = false
shell = false
agent = false
~~~

## Remote servers and login

`--transport` selects `http` (streamable HTTP, the default) or `sse`. `http`
speaks the current MCP transport: every request is a POST, and the session id
and protocol version the server negotiated at `initialize` travel with each
later request. `sse` is the legacy transport — a GET opens an event stream,
and requests are POSTed to the address it hands back. Existing `sse` servers
keep working; `orca mcp add --transport sse` still exists for the rare server
that speaks only the legacy transport.

A remote server authenticates one of three ways:

- **A static header** — `--header "Authorization: ..."`, sent on every
  request.
- **`--bearer-token-env-var VAR`** — `orca` reads `VAR` from its own
  environment at connect time and sends it as a bearer token. The token
  itself is never written to the config file.
- **OAuth**, for a server configured with neither of the above. Run
  `orca mcp login <name>` to authorize it in your browser; the authorization
  url is also printed, for a machine with no browser to open it by hand.
  `orca mcp logout <name>` deletes the saved login. `login` refuses a stdio
  server, or one already using a static header or `--bearer-token-env-var`,
  since neither uses OAuth.

OAuth tokens are stored in `$ORCA_HOME/mcp-credentials.json`, next to
`config.toml` and readable only by its owner, keyed by server name and url —
moving a server to a new url invalidates the login saved under the old one.
`orca mcp list` and `orca mcp get` show each server's auth status
(`oauth: logged in`, `oauth: not logged in`, `bearer: $VAR`, `static header`,
or `-` for a stdio server) without ever printing the token itself.

`login` and `logout` only change configuration or the credential store; they
never touch a session that is already running. A running TUI session picks
up the change by reconnecting the server from the `/mcp` panel.

## Manage servers in the TUI

In the interactive TUI, `/mcp` lists the conversation's servers and how each
stands: connected, with its tool count; failed, with the reason; needing a
login; or disabled. `Enter` shows a server's tools, with the read-only ones
marked, its prompts, and the `enabled_tools`/`disabled_tools` its
configuration sets. `r` reconnects the selected server, `l` logs in to it with
OAuth and then reconnects it, and `o` deletes its saved login and then
reconnects it. Before your first message no server has connected yet: the
panel lists the configured ones as `not connected yet`, and `l` already logs
in, so a server just added with `orca mcp add` can be logged in to before the
conversation starts and connects with that login. See
[Terminal UI](terminal-ui.md#mcp-servers) for the panel and its keys.

## Images from tools

`deepseek-flash` and `auto`, which uses it, are the only models that see the
images an MCP tool returns, inline on the tool message. `deepseek-v4-pro` and
custom models, even ones declared with `supports_images = true`, get a note in
their place saying the model cannot see them. Only PNG, JPEG, GIF, and WebP are
accepted, decoded size up to 5 MiB each; anything else is dropped with a note
explaining why. One MCP response, images included, is limited to 16 MiB; a
larger one fails the call.

Each request carries at most the 3 newest tool images in the conversation;
older ones are replaced with a note. This limits what goes out over the wire
only — the full history stays on disk.

Resuming a session does not reload earlier tool images, regardless of which
model resumes it. The resumed conversation keeps the note in their place.

## Read-only tools

A server can mark a tool read-only in its `tools/list` response
(`readOnlyHint`). Orca then treats a call to that tool as a read:

- Suggest mode does not ask before the call; plan mode allows it, while
  every other MCP tool call is still denied.
- Whether a tool is read-only is entirely up to the server's own
  declaration.
- A tool the server also marks `destructiveHint` is still asked about,
  the same as any other write.

## Always allow

An MCP tool's approval panel offers two extra choices beyond the ones every
tool call gets: `5` always allow this tool (saved) and `6` always allow this
server (saved). Both run the call and, like `3` allow for this session, stop
asking for the rest of the session; they additionally append an allow rule to
the user configuration so a future session skips the prompt too:

~~~toml
[[permissions.rules]]
tool = "mcp__github__create_issue"
decision = "allow"

[[permissions.rules]]
tool = "mcp__github__*"
decision = "allow"
~~~

The first rule (`5`) names one tool; the second (`6`) covers every tool on
that server. Neither writes a `pattern`, since an MCP tool call has none —
see [Permission rules](approval-modes.md#permission-rules). If the rule
cannot be saved (an existing config that fails to parse, for example), the
call still runs and the rest of this session still skips the prompt; the
conversation explains that saving the rule failed.

## Operate safely

1. Start with a read-only capability set.
2. Use absolute paths for local server programs.
3. Review a workspace before trusting its project configuration.
4. Use orca doctor to validate local configuration and sandbox readiness; it
   is intentionally read-only and does not start MCP servers.
5. Check how each server stands in the TUI's `/mcp` panel, and reconnect it
   there.

`orca mcp list` and `orca mcp get` inspect configured servers without ever
printing credential values; `env` and `headers` show only the configured key
names. There is no CLI command to restart, test, or diagnose a running MCP
connection: a running connection belongs to its session, and the TUI's `/mcp`
panel shows its status and reconnects it.
