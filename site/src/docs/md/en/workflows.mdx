# Workflows

Workflows are persisted local programs that coordinate multiple agent calls.
The public CLI exposes their lifecycle through orca workflow.

~~~text
orca workflow run [OPTIONS] <SCRIPT_OR_NAME>
orca workflow list [--name NAME] [--run-id RUN_ID] [--status STATUS]
orca workflow show <TASK_ID>
orca workflow source <NAME>
orca workflow stop <TASK_ID>
orca workflow pause <TASK_ID>
orca workflow resume <RUN_ID>
orca workflow clone <RUN_ID>
orca workflow restart-failed <RUN_ID>
orca workflow restart-phase <RUN_ID> <PHASE>
~~~

## Run a workflow

~~~bash
orca workflow run ./workflows/review.js --cwd ./my-project
orca workflow run review --args '{"base":"main"}'
orca workflow run review --resume-from-run-id RUN_ID
~~~

run accepts --cwd, --model, --api-key, --base-url, --args, and
--resume-from-run-id. It does not accept the headless orca exec budget or
output options; inspect orca workflow run --help before automating a launch.

A named workflow resolves from the configured workflow locations; a path names
the script directly. Workflow scripts are JavaScript modules with a declared
metadata export, not YAML files. Keep the script, its verifier logic, and its
input schema under version control.

## Shared execution capacity

Workflow agent calls do not create a separate worker pool. They share the root
task tree's durable subagent execution scope with direct, nested, hosted, and
resumed children. When `max_running` is full, accepted work stays queued without
starting a worker. A parent waiting through `task_wait` releases its execution
lease at a safe checkpoint and must reacquire one before continuing.

The same task controls apply to workflow children and direct subagents:
`task_list`, `task_wait`, `task_read_output`, `task_send_input`, and
`task_stop`. The retired `subagent_status` tool and model-facing sync/async mode
are not part of the current protocol.

## Observe and recover

~~~bash
orca workflow list --status running
orca workflow show TASK_ID
orca workflow pause TASK_ID
orca workflow resume RUN_ID
~~~

Use show to inspect one persisted run. A pause, stop, restart, or clone is
scoped to its recorded task or run ID. A resumed workflow reuses only durable
completed boundaries; an interrupted tool action remains potentially applied
until its target state is checked.

The TUI is the richer surface for live child-agent activity. The command line
is intentionally limited to launching, inspecting, and controlling persisted
workflow runs.
