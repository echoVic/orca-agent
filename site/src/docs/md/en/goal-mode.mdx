# Goal-Oriented Tasks

Orca's public CLI does not require a separate goal file format. Put the
objective, boundaries, and acceptance check in the task request, then use
execution limits and a verifier to make those boundaries executable.

~~~bash
orca exec \
  --mode suggest \
  --max-turns 20 \
  --max-tool-calls 80 \
  --max-cost-usd 3 \
  --verifier "npm test -- --runInBand" \
  "Fix token refresh. Change only src/auth and its tests; explain any blocked dependency."
~~~

## A useful task specification

For work that matters, state four things:

1. **Outcome**: what must be true when the task is complete.
2. **Scope**: files, systems, and actions that are in or out of bounds.
3. **Budget**: turns, tool calls, cost, and wall-clock limits where relevant.
4. **Evidence**: a verifier command or another observable completion check.

The approval mode is a fifth, independent constraint. plan remains read-only;
suggest, auto-edit, and full-auto select progressively broader execution
policies. Review the workspace and its trust decision before choosing a mode
with write or network capability.

## Repeatable work

Put a long prompt in a repository-owned script or CI job, not in a custom
command namespace. That keeps the objective reviewable beside the verifier and
makes the invocation portable:

~~~bash
orca exec --output-format jsonl --save-history \
  --verifier "./scripts/verify-auth.sh" \
  "$(cat .orca/tasks/fix-token-refresh.txt)" > run.jsonl
~~~

When a recorded run stops before completion, resume it with a new positional
instruction. Do not assume an interrupted tool call was rolled back.
