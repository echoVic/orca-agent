# Computer Use (macOS)

## What it can do

Orca can see and operate other macOS apps with the `computer` tool: list or
launch apps, inspect windows, click, type, send keys, and scroll. Use it to
check a UI you just built, work in an app without a command-line interface,
or work in an app you name. When you name an app, Orca should complete the
work there. For other tasks, prefer file and
command-line tools when they can do the job. App launches use `launch_app`;
shell `open` and `osascript` cannot reach apps from Orca's sandbox.

## Requirements

Computer use is available on macOS 14 or later, in the main session of the
interactive TUI. Give the terminal running Orca **Accessibility** and
**Screen Recording** permissions in **System Settings → Privacy & Security**.
Restart the terminal after granting Screen Recording if the permission has
not taken effect. Also grant **Input Monitoring** if the driver reports
missing listening access when installing the Esc listener; this does not
replace Accessibility permission.

## App approval

Before Orca first observes or operates an app, it asks for approval, unless a
permission rule already decides the call or the session is in `full-auto` (see
[Approval modes](#approval-modes)). The panel offers:

- `1` **Allow once**: run this call; later calls ask again.
- `2` **Allow this app this session**: skip approval for this app until you quit.
- `3` **Allow all apps this session**: skip approval for every app until you quit.
- `7` **Always allow this app (saved)**: save an allow rule for this app for future sessions.
- `5` **Always allow all apps (saved)**: save an allow rule for every app for future sessions.
- `4` **Deny**: refuse the call and stop the turn so you can ask for another way.

Outside `full-auto`, terminals and IDEs need approval for that app itself:
`1`, `2`, or `7`, or an allow rule whose `pattern` is the exact bundle id.
**Allow all apps this session**, `pattern = "*"` or another wildcard, and a
whole-tool allow rule do not cover them. Their approval panel does not offer
the two all-app options.

The saved options write to the user configuration, at `$ORCA_HOME/config.toml`
or, when unset, `~/.orca/config.toml`. `7` saves the app's exact bundle id as
the rule's `pattern`, and `5` saves `pattern = "*"`:

~~~toml
[[permissions.rules]]
tool = "computer"
pattern = "com.apple.Safari"
decision = "allow"
~~~

Text entry into a `[secure]` password field asks separately each time, with
only `1` **Allow typing this once** and `4` **Deny**. This applies to `type`
and text-entering `key` actions: printable keys alone or with Shift/Option,
and `Cmd+V` (also with Shift/Option). Navigation and other non-text shortcuts
do not trigger this separate check.

App grants, including those for all apps, do not preapprove password entry,
and neither does `full-auto`. Patterned allow rules, including exact app ids,
wildcards such as `*`, and an explicit `#secure` target, also leave this check
in place. Only a whole-tool allow rule for `computer`,
without a `pattern`, preapproves it for apps that do not run commands. A matching deny rule still takes
precedence; see [permission rules](approval-modes.md#permission-rules). Outside
`full-auto`, no allow rule preapproves password entry in your existing windows.
In `full-auto`, it uses the ordinary `bundle#secure` target, which the
whole-tool rule can preapprove for apps that do not run commands. Window deny
and prompt rules (`bundle#window:<id>`) do not apply there; app deny and prompt
rules still apply.

If a point target or a stale observation reveals a password field only
during delivery, Orca refuses unapproved input and sends no text. The result
instructs the agent to observe again and target the secure field by its element id
to request approval on retry.

## Your windows

Windows that were already open before Orca's first computer-use step for your message are yours, unless
Orca opened them earlier in this session. Before Orca first observes or
operates one of them, it asks about that window, naming its title:

- `1` **Allow this window once**: run this call; later calls on the window ask again.
- `2` **Allow this window this session**: skip approval for this window until you quit.
- `4` **Deny**: refuse the call; Orca opens a new window instead, for example with Cmd+N.

Outside `full-auto`, app grants, including **Allow all apps this session**,
and allow rules for an app, a wildcard, or the whole tool do not cover your windows;
only the window's own approval does. Deny and prompt rules for an app still apply to
its windows. Without a window named, Orca leaves your windows alone: it uses a
window it opened, or the model opens one (Cmd+N still reaches an app whose
windows are all yours). Windows Orca opens are its own for the rest of the
session. `full-auto` does not ask about windows, as it does not ask about
apps; password entry still asks unless a whole-tool `computer` allow rule
preapproves it for an app that does not run commands. In that mode its target
is `bundle#secure`, so window deny and prompt rules do not apply; app deny and
prompt rules still apply.

In apps where Cmd+N does not open a window (Notes, for example, starts a new
note), it acts in your frontmost window instead, and the result says that no
new window opened.

Opening a file or URL with `launch_app` can also land in one of your windows when the app reuses it (a browser may add a tab); the result says so.

Cmd+Q, Cmd+Option+Q (Quit and Keep Windows), Cmd+Option+W (Close All),
Cmd+Option+M (Minimize All) and Cmd+H (Hide) act on every window of an app
and are refused while your windows are open in it (`full-auto` does not refuse them).

`list_apps` lists window titles only for apps Orca has used in this session,
marking yours `(yours)`; for other apps it shows only how many windows they
have.

Known limits: a window you open after Orca's first computer-use step for your message counts
as Orca's, and so do windows an app restores when Orca launches it. An app that reuses one of its closed windows for a newly opened document (Preview, for example) can make Orca ask about that window.

## App risk levels

Keychain Access (`com.apple.keychainaccess`), Passwords (`com.apple.Passwords`),
apps whose bundle ids start with `com.1password.`, `com.agilebits.`, or
`com.bitwarden.`, and apps declaring the `public.app-category.finance`
category are blocked by default. Only an allow rule whose `pattern` exactly
equals that app's bundle id lifts this default block; a wildcard or whole-tool
allow does not:

~~~toml
[[permissions.rules]]
tool = "computer"
pattern = "com.apple.Passwords"
decision = "allow"
~~~

Orca can never operate its own host terminal, regardless of rules; if the
host cannot be identified, all listed terminal apps are blocked. Other
listed terminals (Terminal, iTerm2, Ghostty, Warp, kitty, Alacritty, WezTerm,
cmux) and IDEs (VS Code, apps under `com.todesktop.` or `com.jetbrains.`,
Xcode, Zed) warn that they can run commands outside Orca's sandbox. Outside
`full-auto`, these apps require their own approval as described above.
Finder warns about file access, System Settings about changing settings,
and listed browsers (Safari, Chrome, Firefox, Arc, Edge, Brave) about web
pages carrying instructions aimed at the agent. The warning appears in the
approval panel and in the app's first result in each session, so calls that
run without a panel, in `full-auto` or under a rule or grant, still show it.

## Approval modes

Plan mode permits only `list_apps` and `observe`; launching, clicking,
typing, sending keys, and scrolling are refused. `list_apps` needs no app
approval. In `plan`, `suggest`, and `auto-edit`, app calls, `observe`
included, ask for app approval unless an applicable rule or grant already
allows them.

`full-auto` already runs commands on the host, so app calls run there without
app approval. Password entry still asks each time unless a whole-tool
`computer` allow rule preapproves it for an app that does not run commands.
App deny and prompt rules still apply; window deny and prompt rules do not,
because targets omit the window id in this mode. Apps blocked by default stay
blocked.

## Observations and screenshots

Use element ids from the latest observation when available. If the tree
lists omitted elements, use `query` to narrow the results by role, label, or
value. A `truncated` observation means the accessibility walk reached its
time limit or depth limit, or skipped a stale subtree, and returned a partial tree;
a control missing from that tree may still exist. Observe again with `query`
or use point targets from the latest screenshot, then inspect the result to
confirm the action.

Coordinates use screenshot pixels, with the origin at the top left. An app
with no content element tree may still list its title-bar buttons; use
point targets for its content.

Click the `[N image(s) attached]` line under the tool result to preview the
screenshot (for example, `[1 image attached]`). Press `q` to close the preview.

## Stop

After the first `computer` call has run, Orca captures `Esc` system-wide
until the turn ends. `Esc` interrupts the running turn, including while
another app is in the foreground or a screenshot preview is open.

Press `4` (Deny) to keep the window and let Orca continue. Esc can stop the
whole turn instead: once a computer call has run in the turn, Orca's Esc
listener stops the turn even while this panel is open. App and password-entry
denials stop the turn.

## Background and foreground

Orca tries to operate apps in the background. When an action needs the
foreground, it briefly switches to the app and then restores the previous
foreground app and pointer; the result says when the foreground was used.
`launch_app` starts an app or opens a URL/file without requesting activation;
an app may still choose to activate itself.
A `key` action containing Command always uses this switch, because Command
shortcuts sent to a background app do not reach it.

To turn off the switch, set this in your user configuration (the default is
`true`; project configuration cannot set it):

~~~toml
[computer_use]
foreground_fallback = false
~~~

Actions that need the foreground, including Command shortcuts, then fail
instead of switching apps.

## When an app keeps failing

When computer actions on one app fail three times in a row, Orca tells the
model to stop trying workarounds and report what failed. After six failures
in a row, Orca stops using that app for the rest of the turn; it is available
again after your next message. A success resets the count. Validation errors
and timeouts count; approval denials, cancellation and `list_apps` do not.

For apps Orca has used in this session, `list_apps` shows the windows it can
observe, checked through Accessibility, and marks minimized windows. For an
app that does not answer that check in time, it lists the app's visible
document-sized windows instead, which observe may still refuse.

When an app has no window yet (for example, TextEdit showing only its Open
panel), a Command or Control shortcut such as Cmd+N can be sent to the app
without a window; Escape is also allowed, but text-entering keys are not.
This needs foreground switching, and a window that appears during activation
gets no unobserved input. When all of an app's windows are yours, or Finder
shows only its desktop, only a lone Cmd+N can use this path. The driver never
observes or operates the desktop or floating windows.

Window errors distinguish an unusable id, a window not yet observed, a changed
window, and an app with no window, with a next step for each. If raising a
window fails but it is already the app's focused window, Orca can continue;
otherwise it retries once. Input must still reach the selected window, and
cover checks still apply.

## Disable computer use

Add a whole-tool deny rule to your user configuration, without a `pattern`.
Orca then leaves `computer` out of the tools available to the model:

~~~toml
[[permissions.rules]]
tool = "computer"
decision = "deny"
~~~

## Privacy

Screenshots can contain private information and are sent to the model
provider when using `deepseek-flash` (including the legacy names
`deepseek-v4-flash` and `deepseek-v4-flash-vision-exp`) or `auto`. Other model
selections receive the accessibility element tree and other text results,
with a note in place of the screenshot; tool screenshots are not sent to a
separate vision model.

## Not supported yet

Dragging and directly setting a field's value are not supported. Computer use
is unavailable to subagents, workflow children, ACP clients, and `orca exec`.

Recognition of UU Remote's full-screen overlay has been added to allow foreground
actions when no other window covers the target app. This path has not yet been
tested in an active UU Remote session. Other remote-control apps'
overlays may still block foreground actions until the remote session is
disconnected.
