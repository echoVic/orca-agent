# Terminal UI

Running `orca` with no task opens the interactive terminal UI. This page walks
through what is on screen and the keys that drive it. For the complete key
list at any time, press `?` (or `F1` / `Ctrl+K`) while the input is empty.

## First run in a folder

The first time Orca opens a folder it asks you to review the workspace
boundary: the workspace path, where the API key is read from, the folder-trust
decision, and a summary of `orca doctor`.

~~~text
╭ Welcome ─────────────────────────────────────────────────────────╮
│ Before the first run, review this workspace security boundary.   │
│ Workspace: ~/projects/api                                        │
│ Folder trust: untrusted                                          │
│                                                                  │
│ › T  Trust workspace                                             │
│   U  Continue untrusted                                          │
│   E  Exit                                                        │
╰──────────────────────────────────────────────────────────────────╯
~~~

Trusting a folder lets Orca load that project's configuration, instructions,
skills, agents, and workflows. It does not enable or bypass the OS sandbox.
See [Approval modes](approval-modes.md) and [Configuration](configuration.md).

Nothing runs until you have answered (and, when no API key is set, entered
one): a prompt given on the command line, as in `orca "fix the failing test"`,
is sent once you accept; a conversation named with `--continue` or `--resume`
opens only then; and the MCP servers wait too. Choosing `E` exits without
sending the prompt, opening the conversation, or starting any server.

## The screen

A conversation reads top to bottom, with the input and the status bar at the
bottom:

~~~text
 ›  fix the failing auth test
    ⋯ thinking · the boundary second is still treated as valid…
    ✓ read  src/auth/token.rs
    │ pub fn token_valid(now: u64, expiry: u64) -> bool {
    └ +2 lines · ctrl+o to expand
    ✎ edit  src/auth/token.rs
    │ edited src/auth/token.rs
 ●  token_valid now rejects the expiry second; the auth test passes.
────────────────────────────────────────────────────────────────────────────
 ›  Message Orca…  / commands · @ files · $ skills
────────────────────────────────────────────────────────────────────────────
 ⇧Tab suggest      deepseek-flash · max · ctx 97% · 8.7k · $0.0031 · ? help
~~~

| Mark | Meaning |
| --- | --- |
| `›` | Your message. |
| `●` | Orca's reply. |
| `⋯ thinking` | The model's reasoning, collapsed to one line. |
| `✓` `✎` `✗` | A tool call that succeeded, edited a file, or failed, with its output under a `│` rail. |
| `ℹ` | A notice from Orca. Long notices collapse like tool output. |

A collapsed row ends with `+N lines · ctrl+o to expand`. Press `Ctrl+O` to
expand the latest one, `Ctrl+Shift+O` to expand all of them, or click a row.

The status bar shows the approval mode on the left (`⇧Tab` cycles it). On the
right are the model and reasoning effort, how much of the context window is
left, the tokens and cost so far, and the help hint. A wide terminal also shows
the folder and git branch in the middle; as the terminal narrows, the tokens
and cost drop out first, then the context, then the model.

## Writing a message

| Key | Action |
| --- | --- |
| `Enter` | Send the message. |
| `Shift+Enter` / `Alt+Enter` | Insert a newline. |
| `@` | Mention a file, skill, plugin, or MCP resource. |
| `$` | Insert a skill. |
| `/` | Open the command menu. |
| `↑` / `↓` | Browse earlier messages when the input is empty. |
| `Ctrl+V` | Attach an image from the clipboard. |
| `Esc` | Clear the draft. `↑` brings it back until you send another message. |

With an empty input, `Esc` takes back your last message: the conversation
rewinds to before it and the message returns to the input so you can edit it.

## While Orca works

A running turn shows an activity line above the input:

~~~text
 ⠼ Running 12s · edit src/auth/token.rs · Esc interrupt
 Queued 1 · Ctrl+Enter send now · Alt+Up edit latest
 ↳ then run the whole test suite
~~~

- `Esc` (or `Ctrl+G`) interrupts the turn.
- Before its first model request, a turn waits for any MCP server still
  connecting, so the model is offered its tools; the activity line says
  `connecting MCP servers` meanwhile, and `Esc` interrupts the wait with the
  turn.
- `Enter` queues your message. Queued messages run in order once the turn
  finishes, and each appears in the conversation as your next message.
  Interrupting pauses the queue; sending a new message resumes it, and
  `/queue` lists, pauses, or starts it.
- `Ctrl+Enter` sends the message now: the running turn reads it after its
  current step. If the turn cannot take it, it jumps to the front of the queue.
  This needs a terminal with the kitty keyboard protocol, such as Ghostty,
  kitty, or WezTerm.
- `Alt+↑` edits the latest queued message.
- `Ctrl+B` with an empty input moves the turn to the background, where it keeps
  running while you start something else.

## Approvals

When a tool call needs your approval, the input area turns into an approval
panel:

~~~text
╭ Approve · edit ──────────────────────────────────────────────────────────╮
│ src/auth/token.rs                                                        │
│                                                                          │
│ › 1  Allow once               run it now                                 │
│   2  Allow this exact call    remember only this exact call              │
│   3  Allow edit this session  skip approval for this tool until you quit │
│   4  Deny                     ask Orca for another way                   │
│                                                                          │
│ ↑↓ move · 1/2/3/4 pick · Enter confirm · Esc deny                        │
╰──────────────────────────────────────────────────────────────────────────╯
~~~

Press a number, or move with `↑`/`↓` and press `Enter`. `Esc` denies; the turn
then stops, and you can tell Orca what to do instead. When the call has no
specific target (a search, for example), option 2 is not offered. If a preview
is longer than the panel, `PgUp`/`PgDn` page through it.

`Shift+Tab` cycles the approval mode: suggest → auto-edit → full-auto → plan.
Entering full-auto asks for confirmation first. See
[Approval modes](approval-modes.md) for what each mode allows.

## Background work and the tasks dock

Background turns, agents, and long-running commands appear in the tasks dock
under the conversation:

~~~text
 ◆ Tasks · 1 active · 1 needs approval
 ● 1 needs approval
 Enter approve · Esc close
~~~

- `/tasks` shows or hides the dock; `Esc` closes it.
- A turn moved to the background stops at the first tool call that needs an
  answer. Press `Enter` in the dock (with an empty input), or click the row, to
  open that approval. When your current approval mode would run the tool
  without asking, the turn continues by itself and says so.
- When background agents finish while you are idle, Orca continues the
  conversation with their results.

`/agents` opens the Agent Workspace, which lists every task with its status.
Select one and press `Enter`:

- a running agent opens its live conversation, or its live activity while
  another turn is running;
- a finished agent opens its transcript;
- a resumable agent also offers `r` to resume, `R` to retry, and
  `/task-follow-up` to send it a follow-up.

## Plan mode

`/plan` (or `Shift+Tab` to plan) switches to read-only planning. Orca
investigates without changing anything, may ask you questions, and then
proposes a plan:

~~~text
 ●  Here is the plan.
  Proposed Plan
  Token expiry fix
  • reject the expiry second in token_valid
  • add a regression test for the boundary
╭ Plan ready ──────────────────────────────────────────────────────────╮
│ The plan is ready. Choose whether to start implementation.           │
│                                                                      │
│ › 1  Yes, implement this plan  Switch to suggest and start coding.   │
│   2  No, stay in Plan mode     Continue planning with feedback.      │
│                                                                      │
│ ↑↓ move · Enter confirm · PgUp/PgDn review plan                      │
╰──────────────────────────────────────────────────────────────────────╯
~~~

Choosing 1 switches back to the mode you were in before planning (auto-edit
when the conversation started in plan mode) and starts the implementation.
Choosing 2 keeps you in plan mode so you can send feedback. You can switch to
plan mode in the middle of a conversation; `/plan off` leaves it.

When Orca asks questions, answer with the number keys or `↑`/`↓` and `Enter`;
`←`/`→` move between questions, and `Ctrl+T` lets you answer in the chat
instead.

## Recap

`/recap` summarizes the conversation so far in a strip above the input:

~~~text
 ↳ Recap  Fixed the token expiry check and added a boundary test; the full
          suite still needs a run on your machine.
~~~

The full text opens in a panel; `Esc` closes it and clicking the strip opens it
again. When you come back to the terminal after about three quiet minutes,
Orca writes a recap on its own. Recap is not available when the TUI is
attached to a daemon session over ACP.

## Side conversations

`/side` opens a side conversation for a quick question that should not change
the main one. `Ctrl+/` switches between the two, and `Ctrl+C` closes the side
conversation. See [Side conversations](side-conversations.md).

## MCP servers

`/mcp` opens a panel of the conversation's MCP servers, one row each with its
status:

~~~text
╭ MCP servers ─────────────────────────────────────────────────────────────────────╮
│ › docs     connected · 2 tools                                                   │
│   github   failed: connection refused                                            │
│   linear   needs login                                                           │
│   archive  disabled                                                              │
│                                                                                  │
│ ↑↓ select · Enter details · r reconnect · l log in · o log out · Esc close       │
╰──────────────────────────────────────────────────────────────────────────────────╯
~~~

| Key | Action |
| --- | --- |
| `↑` / `↓` | Select a server. |
| `Enter` | Show the selected server's details (below). `Enter` again returns to the list. |
| `r` | Reconnect the server. |
| `l` | Log in to the server with OAuth in your browser, then reconnect it. The authorization url also appears in the conversation, to open by hand. While the login waits for your browser, `l` again cancels it; once your browser is back, the login finishes and can no longer be cancelled. |
| `o` | Delete the server's saved login, then reconnect it; it then needs a login again. |
| `Esc` | Close the panel. |

Reconnecting, logging in, and logging out run in the background and report in
the conversation; closing the panel does not stop them. While one runs for a
server, that server takes no other, except `l` to cancel a login that waits
for your browser: the login stops at once and frees the port the browser
would have come back to, nothing is reconnected, and the conversation says
`login to MCP server <name> cancelled`. `l` and `o` apply only to a server
that logs in with OAuth; see
[MCP integration](mcp-integration.md#remote-servers-and-login).

A server's details show its full status, and then:

- its tools, each with the name a permission rule uses for it, with
  `read-only` in front of it for a read-only tool;
- its prompts, each with its arguments, `<required>` and `[optional]`, and
  its description;
- `prompts unavailable: <reason>` when the server connected but could not
  list its prompts;
- the `enabled_tools`/`disabled_tools` its configuration sets.

~~~text
╭ MCP servers ─────────────────────────────────────────────────────────────────────╮
│ github                                                                           │
│ connected · 2 tools                                                              │
│                                                                                  │
│ Tools · permission rules use the names on the right                              │
│   list_issues   read-only · mcp__github__list_issues                             │
│   create_issue  mcp__github__create_issue                                        │
│ Prompts                                                                          │
│   review_pr <pr> [branch]  Review a pull request                                 │
│                                                                                  │
│ ↑↓ select · Enter details · r reconnect · l log in · o log out · Esc close       │
╰──────────────────────────────────────────────────────────────────────────────────╯
~~~

A rule name keeps its room in an 80-column terminal: a long tool name is cut
short before it is.

`/mcp` opens between turns. The servers of the configuration Orca started
with begin connecting as soon as the TUI opens (on a first run in a folder,
once setup is done), all at once and in the background, so the panel shows
them from the start, before your first
message too: each enabled one reads `starting` until it connects, fails, or
needs a login, and its details list its tools and prompts once it has
connected; a disabled one reads `disabled` and is never connected.
`r`, `l`, and `o` work right away, and the conversation your first message
starts takes the servers over as they are, without connecting them again.
Quitting stops every stdio server, those still connecting too. A server
added with `orca mcp add` while the TUI is open appears after you restart
it. While an action runs, the server's row and details show it
(`reconnecting…`;
`waiting for browser login… (l to cancel)` with the authorization url,
`cancelling login…` once you cancel it, and `finishing login…` once your
browser is back; or `logging out…`). A TUI attached
to a daemon session with `orca attach`
cannot manage the daemon's servers. The daemon connects a session's servers
when it opens the session, so after `orca mcp login <name>` on this machine,
`orca attach new` starts a daemon session that uses the login; a session the
daemon already has open uses it once the daemon restarts and you reattach.

## MCP prompts

Each prompt a connected MCP server offers is a slash command,
`/mcp__<server>__<prompt>`, where `<server>` is the name the server's tools
use: lowercase, with other characters turned into `_` (`My-Server` becomes
`my_server`). Type `/mcp` to list them in the command menu, each with its
description and its arguments, `<required>` and `[optional]`:

~~~text
/mcp__github__review_pr  Review a pull request <pr> [branch]
~~~

Arguments follow the command, separated by spaces, and fill the prompt's
arguments in order; the last one takes the rest of the text, spaces
included. `/mcp__github__review_pr 123 main` sets `pr` to `123` and `branch`
to `main`. An optional argument you leave out is not sent. When a required
argument is missing, or a prompt that takes no arguments gets some, Orca
shows the usage, such as `usage: /mcp__github__review_pr <pr> [branch]`, and
runs nothing. Choosing a prompt that takes arguments in the menu fills in
its command for you to add them. `↑` brings back a prompt command you ran,
as it does a message.

Orca asks the server to fill in the prompt and sends what comes back as your
message: its text, with its images attached. Between turns it goes out at
once; during a turn it is queued, like a message you send then. It goes only
to the conversation you ran it in: if you start, resume, or switch to
another conversation before the server answers, it is not sent, and the
conversation says so. Until the server answers, `Esc` cancels the prompt:
the conversation says `MCP prompt /mcp__<server>__<prompt> cancelled`, and
what the server returns is dropped. The server's own request still runs to
its end. This `Esc` comes before the ones that clear a draft or take back a
message, and the draft stays; while a turn runs, `Esc` interrupts the turn
first, and the prompt runs on. The text
goes out as the server wrote it: an `@path` in it is not a mention, and Orca
reads no file for it. When the server reports an error, or its answer is
empty or more than one message can carry (over 1,048,576 characters of
text, more than 600 images, or images over 5 MiB in all), the conversation
says why and nothing is sent.

A server's prompts appear as soon as it connects, before your first
message too. Run one then, and what the server returns is your first
message, which starts the conversation. While a server is still connecting
and has listed no prompts yet, `/mcp__<server>__…` says
`MCP server <name> is still connecting; try again in a moment.` A TUI
attached to a daemon session with `orca attach` has no MCP prompt commands.

## Moving around the conversation

| Key | Action |
| --- | --- |
| `PgUp` / `PgDn` | Scroll one page. |
| `Ctrl+U` / `Ctrl+D` | Scroll half a page when the input is empty. |
| `Ctrl+Home` / `Ctrl+End` | Jump to the top or the bottom. |
| `Ctrl+F` | Find in the conversation when the input is empty. |
| `Ctrl+L` | Clear the screen. The conversation itself is kept. |

## Sessions

`/resume` opens the session picker. Conversations are grouped by project, with
the current project first; type to filter. The picker can also fork, rename,
archive, or delete a conversation. `/new` starts a new conversation, `/fork`
forks the current one, and `/rename` renames it. When you quit, Orca prints the
`orca --resume <SESSION_ID>` command for the conversation.

See [Conversation continuity](session-commands.md) for resuming from the
command line.
