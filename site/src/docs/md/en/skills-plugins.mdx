# Skills & Plugins


Skills are modular instruction sets that extend Orca's capabilities for specific task domains. They are loaded via `SKILL.md` files and injected into the agent's context. This page covers skill anatomy, loading, and what makes a good skill.

## SKILL.md Anatomy

### Structure

A `SKILL.md` file is a markdown document with a specific structure that Orca recognizes and loads into context.

```markdown
---
name: testing
version: "1.0"
description: "Best practices for writing tests with Orca"
triggers:
  - "test"
  - "testing"
  - "unit test"
  - "integration test"
  - "jest"
  - "vitest"
  - "cypress"
tools:
  - read_file
  - write_file
  - shell
  - grep
  - glob
---

# Testing Skill

## When to Use This Skill

This skill guides Orca in writing comprehensive, maintainable tests. Load it when:
- The user asks to write tests
- The task involves test-driven development
- You need to improve test coverage
- You're setting up test infrastructure

## Core Principles

1. **Test behavior, not implementation** — tests should describe what the code does, not how it does it
2. **Keep tests fast** — unit tests should run in under 100ms each
3. **One assertion per test** — clear failure messages
4. **Use descriptive names** — test names should describe the scenario and expected outcome
5. **Follow the Arrange-Act-Assert pattern**

## Testing Patterns

### Unit Test Structure

```typescript
describe('[Component/Feature]', () => {
  describe('[scenario]', () => {
    it('should [expected behavior]', async () => {
      // Arrange
      const input = ...;
      
      // Act
      const result = await functionUnderTest(input);
      
      // Assert
      expect(result).toBe(expected);
    });
  });
});
```

### Edge Case Checklist

For each function or component, consider:
- [ ] Empty/null/undefined inputs
- [ ] Boundary values (0, max, min, empty string)
- [ ] Invalid types or malformed inputs
- [ ] Concurrent/parallel execution
- [ ] Resource cleanup (files, connections, memory)

## Framework-Specific Guidelines

### Jest / Vitest

```typescript
// Prefer describe/it over test()
describe('UserService', () => {
  describe('createUser', () => {
    it('should create a user with valid data', async () => {
      // ...
    });
    
    it('should reject duplicate emails', async () => {
      // ...
    });
    
    it('should hash the password before storing', async () => {
      // ...
    });
  });
});
```

### Testing React Components

```typescript
import { render, screen, fireEvent } from '@testing-library/react';

describe('LoginForm', () => {
  it('should submit credentials', () => {
    const handleSubmit = jest.fn();
    render(<LoginForm onSubmit={handleSubmit} />);
    
    fireEvent.change(screen.getByLabelText('Email'), {
      target: { value: 'user@example.com' }
    });
    fireEvent.change(screen.getByLabelText('Password'), {
      target: { value: 'password123' }
    });
    fireEvent.click(screen.getByText('Submit'));
    
    expect(handleSubmit).toHaveBeenCalledWith({
      email: 'user@example.com',
      password: 'password123'
    });
  });
});
```

## Anti-Patterns to Avoid

- ❌ Testing internal implementation details
- ❌ Over-mocking (mock only what's necessary)
- ❌ Tests that depend on execution order
- ❌ Tests with random or time-dependent data
- ❌ Tests that test the framework, not the code
- ❌ Extremely long setup blocks (consider factory functions)

## Integration with Orca

When Orca loads this skill, it will:

2. Suggest edge cases from the checklist
3. Generate appropriate test framework code

## Loading Skills

### Automatic Discovery

Orca automatically discovers skills in these locations:

1. **Project level**: `.orca/skills/` in the current working directory
2. **Global level**: `~/.config/orca/skills/`
3. **Built-in**: Orca's built-in skills (testing, refactoring, etc.)

```
┌─ Project Root ─────────────────────────────────────┐
│                                                     │
│  .orca/                                             │
│  └── skills/                                        │
│      ├── SKILL.md          ← Default skill for repo │
│      ├── testing/SKILL.md                           │
│      ├── react/SKILL.md                             │
│      └── typescript/SKILL.md                        │
│                                                     │
└─────────────────────────────────────────────────────┘

┌─ Global Config ───────────────────────────────────┐
│                                                     │
│  ~/.config/orca/skills/                             │
│  ├── code-review/SKILL.md                          │
│  ├── debugging/SKILL.md                            │
│  └── performance/SKILL.md                           │
│                                                     │
└─────────────────────────────────────────────────────┘
```

### Loading Methods

#### 1. Explicit Loading

```
@skill:testing Write unit tests for the authentication module
```

```
$testing Write unit tests for the authentication module
```

#### 2. Trigger-Based Loading

When your message matches a skill's triggers, Orca suggests loading it:

```
You: Write unit tests for the login module

<Callout type="info">

Orca: 💡 The "testing" skill is recommended for this task.       Load it? [Y/n]

</Callout>
```

#### 3. Auto-Loading

Set skills to auto-load for specific projects:

```toml
# .orca/config.toml
[skills]
auto_load = ["testing", "react"]
```

#### 4. Programmatic Loading

```bash
orca skill load testing
orca skill list
orca skill unload testing
```

### Skill Composition

Skills can be composed — multiple skills can be loaded simultaneously:

```
$testing $react $typescript Write tests for the React TypeScript component
```

When composed:
- All loaded skills are merged into the system prompt
- Later skills override earlier ones in case of conflicts
- Trigger detection works across all loaded skills

## What Makes a Good Skill

### Characteristics of High-Quality Skills

| Criterion | Description |
|-----------|-------------|
| **Specificity** | Focuses on a narrow, well-defined task domain |
| **Actionability** | Provides concrete patterns and examples, not just theory |
| **Conciseness** | Total content under 200 lines — the model has limited attention |
| **Example-rich** | Uses code examples for every pattern |
| **Anti-patterns** | Explicitly calls out what NOT to do |
| **Tool-aware** | Tells Orca which tools to use and when |
| **Framework-specific** | Tailored to specific frameworks (React, Vue, etc.) |
| **Up-to-date** | Versioned and maintained |

### Good Skill vs. Bad Skill

| Aspect | Good Skill | Bad Skill |
|--------|-----------|-----------|
| Length | 50–150 lines | 500+ lines |
| Examples | Concrete code samples | Vague descriptions |
| Scope | "Testing React hooks" | "How to write code" |
| Anti-patterns | Explicitly listed | Missing |
| Tools | Specified | Not mentioned |
| Triggers | Specific keywords | Too generic |

### Skill Development Best Practices

#### 1. Start with a Specific Domain

```
✅ Good: "Testing React hooks with @testing-library/react"
❌ Bad: "How to test things"
```

#### 2. Include Code Examples

Every pattern should have a concrete code example:

```markdown
## Pattern: Testing Custom Hooks

```typescript
// Good:
it('should return the counter value', () => {
  const { result } = renderHook(() => useCounter(0));
  expect(result.current.value).toBe(0);
  
  act(() => {
    result.current.increment();
  });
  
  expect(result.current.value).toBe(1);
});
```

#### 3. Define Anti-Patterns

Explicitly call out what not to do:

```markdown
## Anti-Pattern: Testing Implementation Details

❌ Bad:
```typescript
it('should call internalMethod', () => {
  const wrapper = mount(Component);
  wrapper.vm.internalMethod(); // Testing private!
});
```

✅ Good:
```typescript
it('should update the display when clicked', () => {
  render(<Component />);
  fireEvent.click(screen.getByText('Click me'));
  expect(screen.getByText('Clicked!')).toBeInTheDocument();
});
```
```

#### 4. Keep It Concise

```
┌─────────────────────────────────────────────────────────────────┐
│                    Skill Length Guidelines                        │
│                                                                 │
│  < 50 lines:    Too short — probably missing examples           │
│  50–150 lines:  Ideal — focused and actionable                  │
│  150–300 lines: Acceptable — rich but manageable                │
│  > 300 lines:   Too long — split into multiple skills           │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

#### 5. Version Your Skills

```yaml
version: "1.2"  # Follow semantic versioning
```

Update the version when you:
- Add new patterns (minor bump)
- Fix incorrect guidance (patch bump)
- Restructure significantly (major bump)

|-------|----------|-------------|

| `code-review` | review, code review, PR | Code review checklists |
| `debugging` | debug, fix, bug, error | Systematic debugging |
| `performance` | performance, optimize, slow | Performance patterns |
| `security` | security, vulnerability, audit | Security best practices |
| `documentation` | docs, documentation, readme | Generate documentation |
| `api-design` | API, REST, endpoint | API design patterns |
| `database` | database, SQL, migration | Database optimization |
| `react` | react, component, JSX | React-specific patterns |
| `typescript` | typescript, TS, types | TypeScript best practices |

> **Tip:** You can override built-in skills by creating a `.orca/skills/<name>/SKILL.md` file in your project. Project-level skills take precedence over built-in ones.
