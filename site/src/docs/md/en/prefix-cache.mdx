# Prefix Cache

Provider prefix caching can reduce repeated input work when consecutive model
requests share an identical leading prefix. It is a provider optimization, not
an Orca durability or correctness boundary.

## What usually preserves a prefix

- keep the model and system configuration stable across related turns;
- keep related work in one recorded conversation;
- avoid injecting timestamps or other changing text near the start of every
  request; and
- let Orca manage compaction instead of reconstructing history in a script.

Any change to the prefix may reduce or eliminate a cache hit. The provider is
the authority for whether tokens were cached.

## Observe provider-reported usage

When the provider returns cache-token usage, Orca includes it in
usage.updated events:

~~~bash
orca exec --output-format jsonl "Inspect the current implementation" |
  jq -c 'select(.type == "usage.updated") | .payload'
~~~

~~~json
{
  "input_tokens": 45000,
  "output_tokens": 1200,
  "cache_tokens": 18000,
  "total_tokens": 46200,
  "estimated_cost_usd": 0.09
}
~~~

Do not invent a cache-hit rate when cache_tokens is missing. Different
providers may report cache usage differently, and a low cache value does not
mean the task should be replayed.

## Compaction

Context compaction changes the material sent on later turns and can therefore
change cache behavior. Observe context.compaction.started and
context.compacted in a JSONL stream when diagnosing a shift. Those events
describe prompt management; the recorded conversation and terminal tool events
remain the source of truth for recovery.
