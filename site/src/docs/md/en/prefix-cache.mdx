# Prefix Cache

Provider prefix caching can reduce repeated input work when consecutive model
requests share an identical leading prefix. It is a provider optimization, not
an Orca durability or correctness boundary.

## What usually preserves a prefix

- keep the model and system configuration stable across related turns;
- keep related work in one recorded conversation;
- avoid injecting timestamps or other changing text near the start of every
  request; and
- let Orca manage compaction instead of reconstructing history in a script.

Any change to the prefix may reduce or eliminate a cache hit. The provider is
the authority for whether tokens were cached.

Custom-agent definitions are fixed at the session's first turn. Later edits in
`.orca/agents/` or the user agent directory do not change the catalog or
instructions used by that session; start a new session to use the edit.

## Context across requests and restarts

Orca records a context update when its text changes. The date, working mode,
goal, skills, recalled memory, and on-demand MCP catalog can then be reused as
part of the history on later DeepSeek requests. The current plan stays at the
end of each request.

Resuming or forking a recorded session reuses its original system prompt.
Orca appends a notice for every section whose text differs or was removed. A
worktree fork can report both the working directory and the paths named in the
project instructions. Orca rebuilds the prompt when instruction sources stop
applying or the recorded prompt cannot be replayed. Compaction can fold the
updated sections into a new leading prompt.

## Observe provider-reported usage

When the provider returns cache-token usage, Orca includes it in
usage.updated events:

~~~bash
orca exec --output-format jsonl "Inspect the current implementation" |
  jq -c 'select(.type == "usage.updated") | .payload'
~~~

~~~json
{
  "input_tokens": 45000,
  "output_tokens": 1200,
  "cache_tokens": 18000,
  "total_tokens": 46200,
  "estimated_cost_usd": 0.09,
  "service_cost_usd": 0.0,
  "service_usage": {
    "deepseek_searches": 0,
    "deepseek_fetches": 0,
    "deepseek_ocr_pages": 0
  }
}
~~~

Do not invent a cache-hit rate when cache_tokens is missing. Different
providers may report cache usage differently, and a low cache value does not
mean the task should be replayed.

## Compaction

Deep compaction's checkpoint request replays the existing prefix on the same
model. Most of the replayed input can be billed at cache-hit rates when the
prefix is still cached. Look for `purpose: "replay"` under
`context.compacted.payload.observation.summary_requests` to see the provider's
reported cache tokens for that request. Once Orca installs the checkpoint, the
next ordinary turn starts from a changed prefix. See [Context and Compaction](#context-window).
