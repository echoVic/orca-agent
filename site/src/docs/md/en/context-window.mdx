# Context and Compaction

The context window is managed by the runtime during a turn. There is no
separate public command for inspecting or mutating it. Use the interactive TUI
for live context information, or consume the execution event stream in an
automated environment.

~~~bash
orca exec --output-format jsonl "Inspect the current implementation" |
  jq -c 'select(.type == "context.updated" or .type == "context.compacted")'
~~~

context.updated carries the observed token usage and limit for that point in a
run. context.compaction.started and context.compacted identify a runtime
compaction boundary. Treat those events as observations: they explain why an
older detail may no longer be in the immediate prompt, not a license to discard
durable conversation or tool records.

Automatic compaction keeps its result only when it brings the conversation
under the compaction limit or shrinks it by at least a tenth. Otherwise the
history stays as it was, with recent tool results intact, and Orca does not try
again until the conversation has grown by a tenth. This matters when the current
prompt alone is larger than the limit. When a request no longer leaves room for
a reply, compaction always runs and keeps any reduction.

For a task that needs a precise earlier fact, include the file path, test name,
or session boundary in the next prompt rather than relying on an implicit
context guess.

## Large tool results

In a recorded session, Orca saves a completed MCP, external tool, `web_fetch`,
or `web_search` text result when it exceeds an estimated 12,500 tokens. The
model gets the beginning and end of the result and a path to the full text.
It can call `read_file` with `offset` and `limit` or run `grep` on that path.
Those tools can read saved results belonging to the current session.

The files live under `$ORCA_HOME/session-results/<session-id>/spill/` with
owner-only permissions on Unix. The path stays in the result during
micro-compaction, and deleting the session removes its files. If Orca cannot
save the text, the tool returns its usual output. Shell tasks, `read_file`,
`grep`, `glob`, and `task_read_output` use their existing output limits or paging.
