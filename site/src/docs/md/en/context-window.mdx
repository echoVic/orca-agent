# Context Window


Orca operates with a **1 million token** context window — one of the largest in the industry. This page explains how the window is filled, what compaction does, and how to work with large contexts effectively.

## The 1M Token Window

Orca's context window can hold approximately 1 million tokens (~750,000 English words or ~350,000 Chinese characters). This is shared across all elements:

| Component | Typical Token Allocation | Description |
|-----------|------------------------|-------------|
| System prompt | ~5K | Fixed instructions, tool schema, safety rules |
| Project context | 50K–200K | File tree, key files, git status, code search results |
| Conversation history | 100K–500K | All user/assistant turns with tool results |
| Per-turn scratch | 10K–50K | Intermediate reasoning, tool outputs, summaries |
| **Available for model** | **~800K–900K** | The usable portion for the model's reasoning |

> **Note:** The exact distribution varies based on project size and conversation length. Orca dynamically adjusts allocations based on the current state.

## How the Context Is Filled

### Context Assembly Pipeline

Before each model call, Orca assembles the context through a multi-stage pipeline:

```
┌─────────────────────────────────────────────────────────────────┐
│                  Context Assembly Pipeline                       │
│                                                                 │
│  Stage 1: System Prompt                                        │
│  ├── Agent instructions (role, personality, constraints)        │
│  ├── Tool schema (available tools, parameters, descriptions)    │
│  └── Safety rules (blocked patterns, approval policies)        │
│                          │                                      │
│                          ▼                                      │
│  Stage 2: Project Context                                       │
│  ├── Repository file tree (depth-limited)                      │
│  ├── Key files (README, package.json, tsconfig, etc.)           │
│  ├── Git status (modified files, branch, recent commits)       │
│  ├── Code search results (relevant snippets)                   │
│  └── Symbol index (function signatures, type definitions)      │
│                          │                                      │
│                          ▼                                      │
│  Stage 3: Conversation History                                  │
│  ├── User messages (full text)                                 │
│  ├── Assistant responses (text + tool calls)                   │
│  ├── Tool results (stdout, status, file changes)               │
│  └── Summaries (from previous compactions)                     │
│                          │                                      │
│                          ▼                                      │
│  Stage 4: Per-Turn Scratch                                     │
│  ├── Current user message                                      │
│  ├── Pending tool results                                      │
│  └── Intermediate summaries                                    │
│                          │                                      │
│                          ▼                                      │
│  Stage 5: Token Budget Check                                    │
│  └── If > 85% full → trigger compaction                       │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### Dynamic Project Context

Orca doesn't load your entire codebase into the context. Instead, it uses a **dynamic retrieval** approach:


<Steps>
<Step title={"**Always loaded**"}>

File tree (up to depth 3), key configuration files, git status

</Step>
<Step title={"**On-demand**"}>

Individual files are loaded when the model requests them (via `read_file` or `@` mention)

</Step>
<Step title={"**Search-based**"}>

Code search results are injected when the model uses `grep` or `search_code`

</Step>
<Step title={"**Symbol-based**"}>

Type definitions and function signatures are loaded when relevant

</Step>
</Steps>


This keeps the project context compact while still giving the model access to the full codebase when needed.

### Context from @ Mentions

Users can inject specific content into the context using `@` mentions:

```
@src/auth/login.ts    → Loads the file content
@src/components/      → Loads all files in the directory (up to 20)
@skill:testing         → Injects testing skill instructions
@mcp:github:list-repos → Calls the GitHub MCP tool and injects results
@url:https://...      → Fetches and injects a URL
```

## Automatic Compaction

### When Compaction Triggers

Compaction automatically triggers when the context window reaches **85% capacity** (~850K tokens). The threshold is configurable:

```toml
[agent]
context_compaction_threshold = 0.85  # 85% full triggers compaction
```

### Compaction Strategy

Orca uses a **multi-tier compaction strategy** that preserves the most important information:

```
┌─────────────────────────────────────────────────────────────────┐
│                    Compaction Tiers                              │
│                                                                 │
│  Tier 0: Never Compressed                                      │
│  ├── System prompt (fixed size)                                │
│  ├── Project context (latest state)                            │
│  └── Last 5 turns (full fidelity)                             │
│                                                                 │
│  Tier 1: Light Compression                                     │
│  ├── Turns 6-15: Summarize to key points and decisions        │
│  ├── Tool results: Keep status + key output only               │
│  └── File contents: Keep latest version only                  │
│                                                                 │
│  Tier 2: Heavy Compression                                     │
│  ├── Turns 16-30: Condense to 1-2 sentence summaries          │
│  ├── Tool results: Keep status only                           │
│  └── Reasoning traces: Discard completely                     │
│                                                                 │
│  Tier 3: Discarded                                              │
│  └── Turns 31+: Removed from context entirely                  │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### What Gets Preserved

<Callout type="warning">

| Element | Preserved? | Compression | |---------|------------|-------------| | System prompt | ✅ | None | | Project file tree | ✅ | None (always latest) | | Key files | ✅ | None (latest version) | | Git status | ✅ | None (always latest) | | Recent tool calls (last 10) | ✅ | None | | Tool results (last 10) | ✅ | None | | Older tool calls | ⚠️ | Summarized | | Older tool results | ⚠️ | Status only | | User messages (recent) | ✅ | None | | User messages (older) | ⚠️ | Summarized | | Assistant responses (older) | ⚠️ | Summarized | | Reasoning traces | ❌ | Discarded | | Intermediate scratch | ❌ | Discarded |

</Callout>

### Compaction and Prefix Cache

Compaction is carefully designed to **preserve the byte-aligned prefix** of the context. This means:

- The system prompt and project context (which form the prefix) are never compacted
- Only the suffix (conversation history) is compressed
- After compaction, the prefix cache continues to hit for subsequent turns

Without this design, every compaction would invalidate the cache and cause a significant slowdown on the next turn.

## Monitoring Context Usage

### TUI Display

The TUI shows a context usage indicator in the status bar:

```
Context: ████████████░░░░░░░░░░░░  62% | 620K / 1000K tokens
```

When usage exceeds 85%, the indicator turns yellow and compaction begins:

```
Context: ██████████████████████████  87% | 870K / 1000K tokens [compacting...]
```

### CLI Command

```bash
# Check context usage for the current session
orca context usage

# Output:
# Session: 42
# Context: 623,450 / 1,000,000 tokens (62.3%)
#   System:     5,120 tokens
#   Project:  142,300 tokens
#   History:  476,030 tokens
#   Scratch:    0 tokens
# Compactions: 2 (last: turn 18, -120K tokens)
```

### Per-Turn Token Breakdown

```bash
orca context breakdown --session 42 --turn 15

# Output:
# Turn 15 token breakdown:
#   Input tokens:   623,450
#   Output tokens:   34,200
#   Reasoning tokens: 18,500
#   Tool call tokens:  2,100
#   Result tokens:   13,600
#   Cost: $0.62 (flash) / $2.48 (pro)
```

## What to Do When 1M Isn't Enough

### 1. Start a New Session

The simplest solution:

```bash
/new
```

This gives you a fresh context window while preserving the old session for reference.

### 2. Use Goals and Workflows

Goals and workflows are designed for long-running tasks. They automatically manage context across multiple executions:

```yaml
# workflow: Multi-step migration
steps:
  - name: "Phase 1: Schema"
    agent: "Design the new database schema"
    budget: { max_turns: 10 }

  - name: "Phase 2: Migration Script"
    agent: "Write the migration script"
    budget: { max_turns: 15 }

  - name: "Phase 3: Update Code"
    agent: "Update all code references"
    budget: { max_turns: 25 }
```

Each step gets its own context window, and results are passed between steps via `ctx.channel`.

### 3. Use Side Conversations

Offload tangential discussions to side conversations:

```
/side Debug the caching layer
```

<Callout type="danger">

Side conversations share the same project context but have independent conversation history. They don't consume the main context window.

</Callout>

### 4. Fork and Resume

When approaching the limit, fork the session to create a checkpoint:

```bash
# In TUI
/fork checkpoint-1

# Resume from the fork later
/resume checkpoint-1
```

### 5. Reduce Context Footprint

Manually compact by specifying what to keep:

```
/keep-since turn-20
# Discards everything before turn 20, keeping only the last 20 turns
```

Or reduce project context:

```
/ctx-depth 2
# Reduces file tree depth from 3 to 2, saving context
```

### 6. Use MCP for External Memory

Connect MCP servers that can store and retrieve information:

```toml
[[mcp.servers]]
name = "knowledge-base"
command = "npx"
args = ["-y", "@modelcontextprotocol/server-memory"]
```

This lets Orca store information externally and retrieve it on demand, freeing up context for active reasoning.

> **Tip:** For very large codebases, consider breaking tasks into focused sessions rather than trying to hold everything in a single 1M-token window. Orca's session persistence makes this seamless.
