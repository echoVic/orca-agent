# Approval Modes

Approval mode is one input to Orca's effective capability policy. It does not
override folder trust, permission rules, sandbox enforcement, or an explicit
denial. When multiple permission rules match, the strictest result wins.

## Public modes

| Mode | Capability ceiling |
| --- | --- |
| plan | Read-only. Write, network, shell, metadata-write, and child-agent capability are denied. |
| suggest | Workspace-write ceiling with approval required where the runtime asks for it. |
| auto-edit | Workspace-write ceiling with the normal edit policy. |
| full-auto | Broadest capability ceiling; still subject to the platform sandbox and configured denials. |

Choose the narrowest mode that can complete the task. In particular, full-auto
is not permission to bypass OS isolation, workspace trust, or denied roots.

## Select a mode

For a headless run, use --mode:

~~~bash
orca exec --mode plan "Inspect the architecture and propose changes"
orca exec --mode suggest "Fix the failing unit test"
orca exec --mode auto-edit "Apply the reviewed formatter changes"
orca exec --mode full-auto "Run the disposable sandbox task"
~~~

The root interactive command also accepts --mode. Its value can select an
approval mode for a TUI session, or the server and acp protocol transports; do
not combine a transport selection with a task prompt or subcommand.

The configuration file uses a top-level mode value, and the environment
override is ORCA_MODE:

~~~toml
mode = "suggest"
~~~

~~~bash
export ORCA_MODE="suggest"
~~~

CLI options override environment, trusted project configuration, user
configuration, and built-in defaults.

## Change mode in the TUI

`Shift+Tab` cycles the mode: suggest → auto-edit → full-auto → plan. Entering
full-auto asks for an explicit Full Access confirmation first. The status bar
shows the active mode on its left (`⇧Tab suggest`).

Use /mode to inspect the active mode or set one explicitly:

~~~text
/mode
/mode suggest
/mode auto-edit
/mode full-auto
/plan
/plan off
~~~

The settings change is applied through the runtime, not by editing a local
prompt. A mode change applies to this session only and is not saved. When a
task is waiting on an approval, resolve that approval based on the displayed
tool, target, and scope rather than changing mode as a shortcut.

## Answer an approval

When a tool call needs approval, the TUI shows an approval panel in place of
the input:

| Choice | Effect |
| --- | --- |
| `1` Allow once | Run this call. |
| `2` Allow this exact call | Run it, and allow the same tool with the same target again without asking. Not offered when the call has no specific target. |
| `3` Allow `<tool>` this session | Run it, and stop asking for this tool until you quit. For `computer` it reads **Allow all apps this session**. |
| `4` Deny | Do not run it. The turn stops, except on an ordinary existing-window panel: Orca can continue with its own window. `Esc` also denies. |
| `5` Always allow `<tool>` (saved) | MCP tools and computer use. Run it, stop asking for this tool for the rest of the session, and save an allow rule to the user config so future sessions skip the prompt too. For `computer` it reads **Always allow all apps (saved)** and saves `pattern = "*"`. |
| `6` Always allow the `<server>` server (saved) | MCP tools only. Run it, and do the same for every tool on that server, saving a server-wide allow rule instead. |
| `7` Always allow this app (saved) | Computer use only. Run it, remember this app for the session, and save an allow rule for its exact bundle id. |

For an MCP tool call, choices `5` and `6` appear in place of `2`: an MCP
tool call's target is the tool's own name, so allowing that exact call again
would allow nothing more than `3` does. If the rule cannot be saved — an
existing config that fails to parse, for example — the call still runs and the
rest of this session still skips the prompt; a message explains that the rule
was not saved. See [Permission rules](#permission-rules) for the rule shape.

For `computer` calls with an app target, the choices are `1` Allow once,
`2` Allow this app this session, `3` Allow all apps this session, `7` Always
allow this app (saved), `5` Always allow all apps (saved), and `4` Deny. A computer approval with no resolved app target offers only `1` and `4`.

For one of your existing windows, the panel instead offers `1` **Allow this
window once**, `2` **Allow this window this session**, and `4` **Deny**.
Deny, including `Esc` on that panel, keeps the window to yourself and lets the
turn continue. It offers no saved or all-app options. App, wildcard and
whole-tool allow rules do not cover these windows; only an exact window allow
does. `full-auto` skips ordinary window approval, while password entry still
asks separately. See [Your windows](computer-use.md#your-windows) for the
ownership rules and known limits.

Outside `full-auto`, terminals and IDEs need approval for that app itself:
`1`, `2`, or `7`, or an allow rule whose `pattern` is the exact bundle id.
**Allow all apps this session**, `pattern = "*"` or another wildcard, and a
whole-tool allow rule do not cover them. Their approval panel does not offer
the two all-app options.

Password text entry also offers only `1` and `4`, with **Allow typing this
once** as the approval label. It asks separately for each `type` or
text-entering `key` call, including printable keys alone or with Shift/Option
and `Cmd+V`. App grants, grants for all apps, `full-auto`, and patterned allow
rules, including `*` and one naming an explicit `#secure` target, do not
preapprove these calls. Only a whole-tool allow rule
for `computer` without a `pattern` does for apps that do not run commands,
except in your existing windows, where no allow rule preapproves password entry;
matching deny rules still win. See
[Computer use](computer-use.md#app-approval).

If the driver detects a password field only during a point action or from a
stale observation, it refuses unapproved input. Observe again and retry with
the secure field's element id to request approval.

`PgUp`/`PgDn` page through a preview that is longer than the panel.

## Approvals for background turns

A turn moved to the background with `Ctrl+B` stops at the first tool call that
needs an answer, and the tasks dock shows `needs approval`. Press `Enter` in
the dock (with an empty input), or click the row, to open the approval. When
the current mode and permission rules would run that tool without asking, the
turn continues by itself and the conversation notes it.

## Plan mode

In plan mode Orca investigates read-only, may ask clarifying questions, and
finishes with a proposed plan. A **Plan ready** dialog then offers to implement
it, which switches back to the mode you were in before planning (auto-edit when
the session started in plan mode), or to stay in plan mode and refine it. You
can switch to plan mode in the middle of a conversation. See
[Terminal UI](terminal-ui.md).

For `computer`, plan mode permits only `list_apps` and `observe`.
`list_apps` needs no app approval, and `observe` asks for it unless an
applicable rule or grant already allows it. Your existing windows need their
own approval even for observe. Rules cannot permit other computer
actions in plan mode. In `full-auto`, app calls run without app approval; see
[Computer use](computer-use.md#approval-modes).

## Permission rules

Permission rules decide a tool call before the mode does. They live in the user
configuration (`~/.orca/config.toml`); a project's `.orca/config.toml` cannot
set them.

~~~toml
[[permissions.rules]]
tool = "bash"
pattern = "cargo *"
decision = "allow"

[[permissions.rules]]
tool = "bash"
pattern = "rm -rf *"
decision = "deny"

[[permissions.rules]]
tool = "write_file"
pattern = "/etc/**"
decision = "deny"
~~~

`decision` is `allow`, `prompt`, or `deny`; when several rules match, the
strictest wins. A rule matches the tool name and the call's target: the command
line for `bash`, and the path for file tools. In a `bash` pattern, `*` matches
any text, `/` included, so `rm -rf *` also catches `rm -rf /tmp/build`. In a
path pattern, `*` and `?` stay within one directory and `**` crosses
directories. On Windows, matching ignores ASCII case. Rules cannot lift plan
mode's limits.

Without a `pattern`, a rule normally covers every call of its tool, whatever
the target: every path, nested or absolute, and every command. For `computer`,
allow rules still respect the separate window and command-running-app limits
above. Omitting `pattern` is not the same as `pattern = "*"`, which in a path
stays within one directory. Take care
with allow rules: `tool = "bash"` with `decision = "allow"` and no `pattern`
lets Orca run any command without asking.

An MCP tool is named `mcp__<server>__<tool>`, so a rule can name one exactly,
and `mcp__<server>__*` (or just `mcp__<server>`) covers every tool on that
server. Write MCP rules without a `pattern`: an MCP call's target is the
tool's own name, such as `mcp__github__create_issue`, so a pattern can only
repeat what `tool` says. Orca normalizes the server and tool parts of a
rule's `mcp__` name the way it names MCP tools, lowercase with every run of
other characters turned into `_`, so `mcp__My-Server__deleteRepo` names the
tool `mcp__my_server__deleterepo`. The details of a server in the `/mcp`
panel show each tool's name as a rule writes it.

~~~toml
[[permissions.rules]]
tool = "mcp__github__*"
decision = "allow"

[[permissions.rules]]
tool = "mcp__github__delete_repo"
decision = "deny"
~~~

With both rules, every tool on the `github` server runs without asking except
`delete_repo`, which the stricter deny rule refuses.

## Approval recovery

A pending approval stays answerable while its turn is alive. MCP approvals
are not resumed after a restart: their tool definitions can change on
reconnection. Approvals for tools supplied only to the turn are also refused
on restart unless Orca can restore the same definition. Older saved approval
continuations without that proof fail closed. Reopening history does not
authorize a changed or missing tool; inspect the state and start a new request.

## Trust remains separate

Folder trust decides whether a project configuration can contribute settings.
Inspect or change it with the public trust command only after reviewing the
workspace:

~~~bash
orca trust show --cwd ./project
orca trust add --cwd ./project
orca trust remove --cwd ./project
~~~

See [Configuration](configuration.md) for precedence and storage locations.
