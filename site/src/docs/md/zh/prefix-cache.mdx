# 前缀缓存


Orca 利用**字节级前缀缓存**来大幅加速重复的上下文发送。当上下文窗口的部分在回合之间保持不变时，API 服务器可以重用缓存的计算结果，而不是从头重新处理 token。

## 什么是前缀缓存？

前缀缓存是一种优化，API 服务器缓存上下文初始部分（前缀）的键值（KV）张量。在具有相同前缀的后续请求中，缓存的张量会被重用，从而避免冗余计算。

### 工作原理

```
┌─────────────────────────────────────────────────────────────────┐
│                    前缀缓存机制                                  │
│                                                                 │
│  回合 1: [系统提示词][项目上下文][对话回合 1]                    │
│          └─────────────── 已缓存 ──────────────┘                │
│                                                                 │
│  回合 2: [系统提示词][项目上下文][对话回合 1]                    │
│          └─────────────── 已缓存（重用） ──────────────┘        │
│          [对话回合 2：新内容]                                    │
│                                                                 │
│  回合 3: [系统提示词][项目上下文][对话回合 1]                    │
│          └─────────────── 已缓存（重用） ──────────────┘        │
│          [对话回合 2：已缓存] [对话回合 3：新内容]              │
│                                                                 │
│  每个回合，缓存随着更多的对话历史而增长。                       │
│  系统提示词和项目上下文始终从第一回合开始就被缓存。              │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 缓存命中与未命中

| 场景 | 缓存状态 | 影响 |
|------|----------|------|
| 同一会话，下一回合 | 前缀命中 | 处理速度提升 50–80% |
| 新会话，同项目 | 部分命中（仅系统提示词） | 速度提升 20–30% |
| 不同项目 | 未命中 | 完整处理时间 |
| 模型已更改 | 未命中 | 完整处理时间 |
| 压缩后 | 部分命中（保留前缀） | 速度提升 30–50% |

## 字节级对齐

Orca 确保上下文前缀为**字节级对齐**，以实现最佳缓存效果。这意味着：

### 稳定排序

上下文始终以相同的顺序组装：


<Steps>
<Step>

系统提示词（固定不变）

</Step>
<Step>

项目上下文（按路径排序，深度受限）

</Step>
<Step>

对话历史（按时间顺序）

</Step>
<Step>

每回合草稿（仅当前回合）

</Step>
</Steps>


排序的任何偏差都会破坏缓存。Orca 严格强制执行这一点：

```
✅ 良好（可缓存）：
[系统] → [项目：src/, tests/, docs/] → [回合 1, 回合 2, 回合 3]

❌ 不良（不可缓存）：
[系统] → [项目：tests/, src/, docs/] → [回合 3, 回合 1, 回合 2]
```

### 什么会破坏缓存

| 操作 | 缓存影响 |
|------|----------|
| 同一会话中的新消息 | 扩展缓存（保留前缀） |
| 模型切换 | 完全缓存未命中 |
| 项目文件变更 | 部分未命中（项目上下文变更） |
| 审批模式变更 | 通常无影响（不影响前缀） |
| 压缩 | 部分命中（保留前缀） |
| 新会话 | 完全缓存未命中 |
| 重启 Orca | 完全缓存未命中（服务器端缓存过期） |

## 推理重放

Orca 前缀缓存最强大的特性之一是**推理重放**。当模型对任务执行广泛推理时，该推理成为对话历史的一部分。在后续回合中，模型可以"重放"其之前的推理：

```
回合 1 推理：
"我需要重构登录流程。让我追踪调用路径：
login() → validateCredentials() → checkSession() → generateToken()
问题在于 checkSession() 没有验证 token 过期时间。
我需要在生成新 token 之前添加过期验证。"

回合 2（在回合 1 推理上缓存命中）：
模型："根据我之前的分析，我需要修改 checkSession()
以添加 token 过期验证。让我也检查一下测试覆盖率。"
```

## 压缩和缓存保留

Orca 的压缩策略旨在**最大化缓存保留**：

- **系统提示词永不改变**：始终是第一个元素，始终被缓存
- **项目上下文仅限最新版本**：文件变更时，只有变更的部分会使缓存失效
- **压缩保留前缀**：旧回合被压缩为摘要，而不是从前缀中移除
- **摘要具确定性**：压缩后的回合每次都生成相同的摘要文本，保持可缓存性

## 多运行收益

前缀缓存在多次运行之间提供复合收益：

### 同一会话，多回合

```
回合 1：缓存未命中（构建前缀）
回合 2：在回合 1 上缓存命中 → 速度提升 60%
回合 3：在回合 1-2 上缓存命中 → 速度提升 70%
回合 10：在回合 1-9 上缓存命中 → 速度提升 80%
回合 20：在回合 1-19 上缓存命中 → 速度提升 85%
```

### 相同项目，多个会话

```
会话 A：缓存未命中（构建项目前缀）
会话 B（同项目）：在项目上下文上部分命中 → 速度提升 30%
会话 C（同项目）：部分命中 + 系统提示词命中 → 速度提升 35%
```

## 衡量缓存命中率

### 内置指标

Orca 在多个位置报告缓存命中率：

#### 每回合显示（TUI）

```
回合 5：3.2s | 45K tokens | 18K 已缓存 (40%) | $0.09
回合 6：2.8s | 52K tokens | 35K 已缓存 (67%) | $0.10
回合 7：2.1s | 48K tokens | 42K 已缓存 (88%) | $0.09
```

#### 会话摘要

```bash
orca sessions show 42

# 输出：
# 会话：42
# 回合数：23
# 总 token：1,240,000
# 已缓存 token：890,000 (71.8% 命中率)
# 总时间：62s
# 缓存节省：180s 处理时间
# 费用：$1.24
# 有效费用（扣除缓存后）：$0.35
```

> **提示：** 如果你始终看到缓存命中率低于 30%，说明有东西在破坏前缀。常见原因：未排序的文件注入、系统提示词中的动态时间戳、或更改项目目录。使用 `orca context inspect` 诊断。
