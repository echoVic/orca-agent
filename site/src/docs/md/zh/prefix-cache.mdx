# 前缀缓存

当连续模型请求具有完全相同的开头时，提供商的前缀缓存可能减少重复输入计算。它只是提供商优化，不是 Orca 的持久化或正确性边界。

## 哪些做法通常有利于保持前缀

- 相关回合使用稳定的模型和系统配置；
- 相关工作放在同一条已记录会话中；
- 避免在每次请求开头注入时间戳等变化文本；
- 让 Orca 管理压缩，不要在脚本中自行重建历史。

前缀中的任何变化都可能减少或取消缓存命中。token 是否被缓存，以提供商返回的信息为准。

## 观察提供商 usage

如果提供商返回缓存 token 用量，Orca 会把它写入 usage.updated 事件：

~~~bash
orca exec --output-format jsonl "检查当前实现" |
  jq -c 'select(.type == "usage.updated") | .payload'
~~~

~~~json
{
  "input_tokens": 45000,
  "output_tokens": 1200,
  "cache_tokens": 18000,
  "total_tokens": 46200,
  "estimated_cost_usd": 0.09
}
~~~

cache_tokens 缺失时不要自行推导命中率。不同提供商可能采用不同的缓存计量方式，缓存值低也不意味着应当重放任务。

## 压缩

上下文压缩会改变后续回合发送给模型的材料，因此也可能改变缓存行为。排查变化时，可在 JSONL 流中观察 context.compaction.started 和 context.compacted。它们描述的是提示词管理；恢复时仍应以已记录会话和工具终态事件为准。
