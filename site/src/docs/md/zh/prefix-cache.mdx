# 前缀缓存

当连续模型请求具有完全相同的开头时，提供商的前缀缓存可能减少重复输入计算。它只是提供商优化，不是 Orca 的持久化或正确性边界。

## 哪些做法通常有利于保持前缀

- 相关回合使用稳定的模型和系统配置；
- 相关工作放在同一条已记录会话中；
- 避免在每次请求开头注入时间戳等变化文本；
- 让 Orca 管理压缩，不要在脚本中自行重建历史。

前缀中的任何变化都可能减少或取消缓存命中。token 是否被缓存，以提供商返回的信息为准。

自定义代理的定义在会话的第一轮固定。在此之后修改 `.orca/agents/` 或用户代理目录中的文件，
不会改变当前会话的代理列表和启动指令；新建会话后才会采用修改。

## 观察提供商 usage

如果提供商返回缓存 token 用量，Orca 会把它写入 usage.updated 事件：

~~~bash
orca exec --output-format jsonl "检查当前实现" |
  jq -c 'select(.type == "usage.updated") | .payload'
~~~

~~~json
{
  "input_tokens": 45000,
  "output_tokens": 1200,
  "cache_tokens": 18000,
  "total_tokens": 46200,
  "estimated_cost_usd": 0.09,
  "service_cost_usd": 0.0,
  "service_usage": {
    "deepseek_searches": 0,
    "deepseek_fetches": 0,
    "deepseek_ocr_pages": 0
  }
}
~~~

cache_tokens 缺失时不要自行推导命中率。不同提供商可能采用不同的缓存计量方式，缓存值低也不意味着应当重放任务。

## 压缩

深度压缩生成检查点时，会用当前模型回放已有的对话前缀。前缀仍在缓存中时，回放的大部分输入可以按缓存命中价计费。在 JSONL 流的 `context.compacted.payload.observation.summary_requests` 中，查看 `purpose: "replay"` 对应的服务端缓存 token 数。采用检查点后，下一次普通请求会从更新后的前缀开始。参见[上下文与压缩](#context-window)。
