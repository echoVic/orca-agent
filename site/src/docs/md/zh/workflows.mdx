# 工作流

工作流是协调多个 Agent 调用的本地持久化程序。公开 CLI 通过 orca workflow 提供其生命周期操作。

~~~text
orca workflow run [OPTIONS] <SCRIPT_OR_NAME>
orca workflow list [--name NAME] [--run-id RUN_ID] [--status STATUS]
orca workflow show <TASK_ID>
orca workflow source <NAME>
orca workflow stop <TASK_ID>
orca workflow pause <TASK_ID>
orca workflow resume <RUN_ID>
orca workflow clone <RUN_ID>
orca workflow restart-failed <RUN_ID>
orca workflow restart-phase <RUN_ID> <PHASE>
~~~

## 运行工作流

~~~bash
orca workflow run ./workflows/review.js --cwd ./my-project
orca workflow run review --args '{"base":"main"}'
orca workflow run review --resume-from-run-id RUN_ID
~~~

run 支持 --cwd、--model、--api-key、--base-url、--args 和 --resume-from-run-id。它不接受无头 orca exec 的预算或输出参数；自动化之前先查看 orca workflow run --help。

名称形式从配置的工作流目录解析；路径形式直接指定脚本。工作流脚本是带元数据导出的 JavaScript 模块，不是 YAML 文件。应把脚本、验证逻辑和输入模式放进版本控制。

## 共享执行容量

Workflow agent 调用不会创建独立 worker 池。它们与直接、嵌套、托管和恢复的子代理
共用根任务树的持久执行作用域。`max_running` 满额时，已接受任务保持排队且不会
提前创建 worker。父代理通过 `task_wait` 等待时会在安全检查点释放执行 lease，
继续运行前必须重新取得名额。

Workflow 子任务与直接子代理共用 `task_list`、`task_wait`、
`task_read_output`、`task_send_input` 和 `task_stop`。旧的
`subagent_status` 以及模型可见的 sync/async 模式不再属于当前协议。

## 观察与恢复

~~~bash
orca workflow list --status running
orca workflow show TASK_ID
orca workflow pause TASK_ID
orca workflow resume RUN_ID
~~~

使用 show 检查一条已持久化运行。暂停、停止、重启和克隆都绑定其任务或运行 ID。恢复的工作流只复用已完成的持久化边界；中断的工具操作在检查目标状态前都应视为可能已经生效。

需要查看实时子 Agent 活动时，TUI 是更完整的入口。命令行刻意只负责启动、检查和控制已持久化的工作流。
