# 上下文窗口


Orca 拥有 **100 万 token** 的上下文窗口——业界最大的窗口之一。本页解释窗口的填充方式、压缩机制以及如何有效处理大上下文。

## 1M Token 窗口

Orca 的上下文窗口可容纳约 100 万个 token（约 75 万个英文单词或约 35 万个中文字符）。该窗口在所有组件之间共享：

| 组件 | 典型 token 分配 | 描述 |
|------|----------------|------|
| 系统提示词 | 约 5K | 固定指令、工具模式、安全规则 |
| 项目上下文 | 50K–200K | 文件树、关键文件、git 状态、代码搜索结果 |
| 对话历史 | 100K–500K | 所有用户/智能体回合及工具结果 |
| 每回合草稿 | 10K–50K | 中间推理、工具输出、摘要 |
| **模型可用** | **约 800K–900K** | 供模型推理的可用部分 |

> **注意：** 确切的分配因项目大小和对话长度而异。Orca 根据当前状态动态调整分配。

## 上下文如何填充

### 上下文组装管道

每次模型调用之前，Orca 通过多阶段管道组装上下文：

```
┌─────────────────────────────────────────────────────────────────┐
│                  上下文组装管道                                   │
│                                                                 │
│  阶段 1：系统提示词                                              │
│  ├── 智能体指令（角色、个性、约束）                              │
│  ├── 工具模式（可用工具、参数、描述）                            │
│  └── 安全规则（被阻止的模式、审批策略）                          │
│                          │                                      │
│                          ▼                                      │
│  阶段 2：项目上下文                                              │
│  ├── 仓库文件树（深度受限）                                     │
│  ├── 关键文件（README、package.json、tsconfig 等）               │
│  ├── Git 状态（已修改的文件、分支、最近提交）                    │
│  ├── 代码搜索结果（相关代码片段）                                │
│  └── 符号索引（函数签名、类型定义）                              │
│                          │                                      │
│                          ▼                                      │
│  阶段 3：对话历史                                               │
│  ├── 用户消息（完整文本）                                       │
│  ├── 智能体响应（文本 + 工具调用）                               │
│  ├── 工具结果（stdout、状态、文件变更）                          │
│  └── 摘要（来自之前的压缩）                                     │
│                          │                                      │
│                          ▼                                      │
│  阶段 4：每回合草稿                                             │
│  ├── 当前用户消息                                               │
│  ├── 待处理的工具结果                                           │
│  └── 中间摘要                                                   │
│                          │                                      │
│                          ▼                                      │
│  阶段 5：Token 预算检查                                         │
│  └── 如果 > 85% 已满 → 触发压缩                                │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 动态项目上下文

Orca 不会将整个代码库加载到上下文中。相反，它使用**动态检索**方法：


<Steps>
<Step title={"**始终加载**"}>

文件树（最多 3 层深度）、关键配置文件、git 状态

</Step>
<Step title={"**按需加载**"}>

当模型请求时加载单个文件（通过 `read_file` 或 `@` 提及）

</Step>
<Step title={"**基于搜索**"}>

当模型使用 `grep` 或 `search_code` 时注入代码搜索结果

</Step>
<Step title={"**基于符号**"}>

在相关时加载类型定义和函数签名

</Step>
</Steps>


这保持了项目上下文的紧凑性，同时仍然赋予模型在需要时访问完整代码库的能力。

## 自动压缩

### 何时触发压缩

当上下文窗口达到**85% 容量**（约 850K tokens）时自动触发压缩。阈值可配置：

```toml
[agent]
context_compaction_threshold = 0.85  # 85% 满时触发压缩
```

### 压缩策略

Orca 使用**多层压缩策略**，保留最重要的信息：

```
┌─────────────────────────────────────────────────────────────────┐
│                    压缩层级                                      │
│                                                                 │
│  层级 0：永不压缩                                               │
│  ├── 系统提示词（固定大小）                                     │
│  ├── 项目上下文（最新状态）                                     │
│  └── 最近 5 回合（完整保真度）                                  │
│                                                                 │
│  层级 1：轻度压缩                                               │
│  ├── 回合 6-15：摘要为关键点和决策                              │
│  ├── 工具结果：仅保留状态 + 关键输出                            │
│  └── 文件内容：仅保留最新版本                                   │
│                                                                 │
│  层级 2：重度压缩                                               │
│  ├── 回合 16-30：压缩为 1-2 句摘要                              │
│  ├── 工具结果：仅保留状态                                       │
│  └── 推理痕迹：完全丢弃                                        │
│                                                                 │
│  层级 3：丢弃                                                   │
│  └── 回合 31+：从上下文中移除                                  │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 压缩和前缀缓存

压缩经过精心设计，**保留上下文的字节对齐前缀**。这意味着：

- 系统提示词和项目上下文（形成前缀）永不压缩
- 仅压缩后缀（对话历史）
- 压缩后，前缀缓存为后续回合继续命中

## 监控上下文使用

### TUI 显示

TUI 在状态栏中显示上下文使用情况指示器：

```
上下文：████████████░░░░░░░░░░░░  62% | 620K / 1000K tokens
```

### CLI 命令

```bash
# 检查当前会话的上下文使用情况
orca context usage

# 输出：
# 会话：42
# 上下文：623,450 / 1,000,000 tokens (62.3%)
#   系统：5,120 tokens
#   项目：142,300 tokens
#   历史：476,030 tokens
#   草稿：0 tokens
# 压缩次数：2（最近：第 18 回合，-120K tokens）
```

## 1M 不够用时怎么办

### 1. 开始新会话

最简单的解决方案：

```bash
/new
```

这会给你一个新的干净上下文窗口，同时保留旧会话以供参考。

### 2. 使用目标和工作流

目标和工作流专为长时间运行的任务而设计。它们自动管理多个执行之间的上下文：

```yaml
# 工作流：多步骤迁移
steps:
  - name: "阶段 1：Schema"
    agent: "设计新的数据库 schema"
    budget: { max_turns: 10 }

  - name: "阶段 2：迁移脚本"
    agent: "编写迁移脚本"
    budget: { max_turns: 15 }

  - name: "阶段 3：更新代码"
    agent: "更新所有代码引用"
    budget: { max_turns: 25 }
```

### 3. 使用侧边对话

将无关的讨论转移到侧边对话：

```
/side 调试缓存层
```

侧边对话共享相同的项目上下文，但拥有独立的对话历史。

### 4. 分叉和恢复

接近限制时，将会话分叉以创建检查点：

```bash
# 在 TUI 中
/fork checkpoint-1

# 稍后从分叉点恢复
/resume checkpoint-1
```

### 5. 使用 MCP 进行外部存储

连接可存储和检索信息的 MCP 服务器：

```toml
[[mcp.servers]]
name = "知识库"
command = "npx"
args = ["-y", "@modelcontextprotocol/server-memory"]
```

这让 Orca 可以在外部存储信息并按需检索，释放上下文用于主动推理。

> **提示：** 对于非常大的代码库，考虑将任务拆分为专注的会话，而不是试图在单个 1M token 窗口中容纳所有内容。Orca 的会话持久化使这一过程无缝衔接。
