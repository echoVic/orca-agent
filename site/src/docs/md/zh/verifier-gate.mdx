# Verifier 门控


Orca 的验证器门控是质量保证机制。它在智能体完成任务后运行独立的验证命令，确保输出确实可用。本页涵盖门控生命周期、好的和差的验证器，以及如何为不同任务类型设计验证器。

## 门控生命周期

### 5 步验证过程

```
┌─────────────────────────────────────────────────────────────────┐
│                    Verifier 门控生命周期                         │
│                                                                 │
│  第 1 步：智能体完成                                            │
│  ├── 智能体完成任务（或预算耗尽）                               │
│  ├── 智能体的工作保存在会话中                                   │
│  └── 控制权交给验证器门控                                      │
│                          │                                      │
│                          ▼                                      │
│  第 2 步：验证器准备                                            │
│  ├── 解析验证器命令（来自标志或配置）                          │
│  ├── 设置环境（工作目录、环境变量）                            │
│  └── 捕获当前文件状态快照                                      │
│                          │                                      │
│                          ▼                                      │
│  第 3 步：验证器执行                                            │
│  ├── 执行验证器 Shell 命令                                     │
│  ├── 捕获 stdout、stderr 和退出码                              │
│  ├── 强制超时（默认：5 分钟）                                  │
│  └── 监控资源耗尽                                              │
│                          │                                      │
│                          ▼                                      │
│  第 4 步：结果分析                                              │
│  ├── 检查退出码：                                              │
│  │     0 → 验证器通过                                          │
│  │     非零 → 验证器失败                                       │
│  ├── 捕获输出供智能体引用                                      │
│  └── 将结果记录在会话数据库中                                  │
│                          │                                      │
│                          ▼                                      │
│  第 5 步：门控决策                                              │
│  ├── 通过 → 退出码 0（成功）                                   │
│  │   └── 智能体的工作已验证                                    │
│  ├── 失败 → 退出码 3（验证器失败）                             │
│  │   └── 智能体的工作可能不完整或不正确                        │
│  └── 超时 → 退出码 3（验证器失败）                             │
│      └── 验证器耗时过长                                        │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 验证器与智能体的集成

验证器门控与智能体循环是分开的：

```
智能体循环：
  回合 1 → 回合 2 → ... → 回合 N → 智能体完成
                                        │
                                        ▼
                                 ┌─────────────┐
                                 │ Verifier    │
                                 │    门控     │
                                 └─────────────┘
                                        │
                          ┌─────────────┴─────────────┐
                          ▼                           ▼
                    通过                         失败
                          │                           │
                    退出 0                       退出 3
                                                  （恢复以修复）
```

## 好的验证器 vs. 差的验证器

### 质量标准

| 标准 | 好的验证器 | 差的验证器 |
|------|-----------|-----------|
| **独立性** | 独立于智能体的主张验证输出 | 依赖智能体的自我报告 |
| **确定性** | 相同输入→每次相同输出 | 非确定性或不稳定 |
| **特异性** | 检查请求的确切更改 | 太宽或太窄 |
| **速度** | 在 2 分钟内运行 | 需要 10+ 分钟 |
| **信号** | 明确的通过/失败标准 | 模糊的结果 |
| **覆盖范围** | 覆盖更改的完整范围 | 仅测试子集 |

### 验证器质量示例

```bash
# ✅ 好：针对特定更改的目标测试
orca exec "修复登录 bug" --verifier "npm test -- --testPathPattern=login"

# ✅ 好：用于全面更改的完整测试套件
orca exec "重构认证模块" --verifier "npm test"

# ✅ 好：类型检查
orca exec "添加 TypeScript 类型" --verifier "npx tsc --noEmit"

# ❌ 差：总是通过
orca exec "任何事" --verifier "echo done"

# ❌ 差：只检查文件是否存在
orca exec "添加新组件" --verifier "test -f src/components/NewComp.tsx"
```

### 按任务类型划分的验证器模式

| 任务类型 | 推荐验证器 |
|----------|-----------|
| Bug 修复 | 目标测试套件（`npm test -- --testPathPattern=X`） |
| 新功能 | 完整测试套件 + 构建检查 |
| 重构 | 完整测试套件 + 类型检查 + lint |
| TypeScript 迁移 | `npx tsc --noEmit` |
| 性能优化 | 比较前后的基准脚本 |
| 文档 | 拼写检查 + markdown lint |
| API 集成 | 健康检查端点 |

## 验证器门控与恢复

### 验证器失败 → 恢复循环

```bash
# 第 1 步：首次尝试
orca exec "修复所有失败的测试" --verifier "npm test"
# 结果：仍有 3 个测试失败 → 退出码 3

# 第 2 步：恢复——智能体看到测试输出并修复更多
orca exec resume <session-id>
# 结果：仍有 1 个测试失败 → 退出码 3

# 第 3 步：再次恢复——智能体专注于剩余的测试
orca exec resume <session-id>
# 结果：所有测试通过 → 退出码 0
```

### 恢复时的验证器输出

在验证器失败后恢复时，智能体自动接收：


<Steps>
<Step>

运行的**验证器命令**

</Step>
<Step>

**stdout 和 stderr** 输出

</Step>
<Step>

**退出码**（非零 = 失败）

</Step>
<Step>

验证器执行的**持续时间**

</Step>
</Steps>


这让智能体确切了解出了什么问题并尝试修复。

> **提示：** 设计快速、独立和具体的验证器。差的验证器比没有验证器更糟糕——它会产生虚假的信心或浪费时间调试验证器而不是实际代码。
