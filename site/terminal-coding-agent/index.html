Why it fits

Orca keeps the coding loop inside your terminal.

Local repository work

Search, read, edit, and verify files without moving code through a separate chat window. Orca runs against the same checkout you already trust, so diffs land in your working tree and your editor sees them immediately.

Approval-aware tools

Reads can move quickly, while edits, shell commands, network calls, MCP tools, and subagents follow policy. Each tool declares its capabilities, and the approval mode decides whether a call runs directly, asks once, or stays blocked.

Long-running tasks

Persistent goals and resumable JSONL history help long refactors continue across turns and restarts. A goal survives the process exiting and auto-continues after successful turns until it is explicitly audited complete or blocked.

Verifier-gated edits

Pair a change with a verifier command such as npm test or cargo check. Orca runs the verifier after edits and only treats the turn as done when the check passes, so regressions surface inside the same loop.

Plan mode for risky work

Before touching files, ask Orca to investigate read-only and write a plan. Plan mode produces a structured proposal with steps, risks, and verification commands, and waits for your approval before execution begins.

Resumable JSONL transcripts

Every message, tool call, approval, and verifier result is appended to a local JSONL transcript under ~/.orca/sessions/. Resume, fork, and search the history without sending it to a third-party service.

How it works

One terminal session, the whole coding loop.

Start from a real checkout

Run orca inside any repository. Orca inherits your working directory, your git state, and your environment, so the first thing it sees is the same code you see. There is no upload step and no separate workspace to keep in sync.

Search and read before editing

Orca uses built-in glob, grep, and read_file tools to locate the relevant files. Because reads are fast and low-risk, they run without approval by default, letting the agent build context before it proposes a single change.

Edit with an explicit diff

Edits go through a capability-checked edit or write_file tool. The approval panel shows the exact diff before it is applied, and the change lands in your working tree so your editor, linter, and tests see it at once.

Run commands in a sandbox

Shell commands execute under a sandbox that defaults to the workspace. Linux hosts prefer bubblewrap and fall back to Landlock plus seccomp; macOS uses Seatbelt. Network and write access outside trusted folders requires explicit approval.

Verify before claiming success

Attach a verifier to the turn with --verifier or inline in the prompt. Orca runs it after each edit and reports the result; a failing verifier keeps the turn open so the agent can fix the regression instead of handing you a broken patch.

Continue across restarts

When a session is interrupted, orca --resume reloads the JSONL transcript and restores the plan, goal, and tool state. Long refactors and multi-step migrations do not have to start over because the terminal closed.

When to reach for it

Built for the work that already lives in your terminal.

Fix a failing test or CI job

Point Orca at the failure: it reads the stack trace, greps for the function, reproduces the issue locally, applies a fix, and reruns the test until it passes. The transcript keeps the reproduction command and the diff together.

Refactor across many files

Large renames and API migrations are where a persistent goal pays off. Orca tracks the remaining call sites, applies edits in batches, and verifies the build after each batch so a mistake is caught before it spreads.

Explore an unfamiliar codebase

Ask Orca to explain a module, trace a request from route to database, or summarize how a feature is wired. It searches the real code instead of guessing, and cites file paths you can open yourself.

Prepare a pull request

From a branch, Orca can stage the right files, write a commit message, run the test suite, and summarize the change for review. Pair it with the GitHub workflow to extend the loop into issues and release checks.

Automate repeatable chores

Dependency bumps, changelog updates, and formatting passes become one prompt with a verifier. Because the transcript is local, you can audit exactly what changed and reuse the pattern the next time.

Debug with a live terminal

Orca can run a long-lived shell session, stream its output, and react to it. For flaky tests or interactive CLIs, the agent keeps the process alive instead of re-running a one-shot command each turn.

FAQ

Questions about the terminal coding agent.

Does Orca run in my existing terminal?

Yes. Orca is a single Rust binary you launch from any shell. It does not replace your terminal; it runs inside it and works against the current working directory.

Can it edit files without my permission?

Not by default. Edits, shell writes, and network calls go through an approval policy. You can allow a tool once, for the session, or keep it blocked, and the default mode keeps reads fast while gating writes.

What happens if the verifier fails?

The turn stays open. Orca sees the verifier output, proposes another fix, and reruns the check. It only reports success when the verifier passes, so you do not inherit a patch that breaks the build.

Is my code sent anywhere?

Orca runs locally and only contacts the model provider you configure. Transcripts, tool outputs, and file contents stay on your machine unless the model API needs them for a request.

Can I resume a session after closing the terminal?

Yes. Sessions are stored as JSONL under ~/.orca/sessions/. Use orca --resume to pick up where you left off, or --fork to branch a session and try an alternative approach.

How does this compare to a chat-based agent?

Orca keeps the repository, the shell, and the transcript in one local process. There is no copy-paste between a chat window and your editor, and the full tool and approval model is available from the first prompt.
