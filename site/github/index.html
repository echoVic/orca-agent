Issue triage

Release checks

Repository archaeology

Local-first, GitHub-aware

Orca runs against your local checkout and uses GitHub for what it is good at: issues, PRs, releases, and search. The repository state never leaves your machine unless you push it, and credentials stay in your environment.

How the GitHub loop works

From issue to release, one local agent.

Start from an issue or a PR

Give Orca an issue number or a PR URL. It fetches the context, reproduces the problem locally, and proposes a fix grounded in the actual code rather than the issue description alone.

Investigate before editing

Orca now searches the real codebase, reads the relevant files, and checks the actual git history. Reads run without approval by default, so the agent can build context fast before it proposes a single change and cites exact file paths in its plan.

Edit and verify in the same turn

Edits go through a capability-checked tool with an explicit diff. Attach a verifier like cargo test or npm test and Orca runs it after each edit, looping until the check passes cleanly.

Prepare the PR

Once the change is fully verified, Orca can quickly stage files, then write a commit message, and also summarize the change for review. The summary cites the files touched, the verifier run, and any risks worth noting so reviewers can focus on judgment instead of archaeology.

Run release checks

Before tagging a release, Orca runs the build, the test suite, the linter, and any custom checks through the verifier model. A failure stops the release before a bad tag is pushed, and the transcript records every check that ran.

Keep an auditable trail

Every issue read, PR inspection, edit, and verifier result is recorded in the local JSONL transcript. You can now audit exactly what Orca did and reuse the pattern for the next release, or extract a trajectory to train on later.

Common workflows

GitHub tasks Orca handles from the terminal.

Triage a bug report

Orca reads the issue, reproduces it locally, traces the root cause through the code, and writes a focused fix with a passing verifier. The transcript keeps the repro and the diff together.

Review a pull request

Point Orca at a PR and it inspects the diff, runs the tests, and flags issues with file paths and line numbers. The review is grounded in the actual code, not just the description, so you get actionable feedback instead of generic suggestions.

Prepare release notes

Orca reads the git log since the last release, groups the changes, and drafts release notes. Pair it with a verifier that checks the changelog format before the release is published.

Find why CI started failing

Orca can bisect the history, read the failing job logs, and trace the regression to a specific commit. It then proposes a fix and reruns the failing check locally so the next green run is the one you push.

Update a dependency safely

Orca bumps the version, runs the build and tests, and reports whether the upgrade is clean. If tests fail, it digs into the breaking change and adapts the code.

Keep the changelog honest

After a change, Orca updates the changelog with the actual files and behaviors touched. A verifier can enforce that every changelog entry references a real change, so the release notes never drift from the code.

FAQ

Questions about Orca for GitHub workflows.

Does Orca push to GitHub automatically?

No. Orca prepares changes locally and runs verifiers, but pushes, PR creation, and releases stay under your control. The default approval model gates git writes just like other edits.

Can it review a PR without checking out the branch?

Orca works against your local checkout. To review a PR, check out the branch and run Orca against it. The agent reads the real files, runs the real tests, and cites real line numbers.

What is a verifier-gated release?

It means a release command only succeeds when every configured verifier passes. If the build, tests, or linter fail, the turn stays open and Orca fixes the regression before the release is tagged.

Is my repository uploaded anywhere?

No. Orca runs locally against your checkout. It only contacts the model provider and, if you use MCP, the tool servers you configure. The repository itself never leaves your machine.

Can Orca work across multiple repositories?

Yes. Run Orca in each repository or use a workspace that contains several. Each session is tied to a working directory, so the agent always knows which checkout it is operating on.

How does this compare to a GitHub Action?

Actions are great for deterministic CI. Orca complements them by handling the investigative and adaptive work: reproducing a flaky failure, understanding a bug, and writing a fix that passes the action.
